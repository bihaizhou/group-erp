## 0. 结论

五类方向都对，本项目里每一类都有对应实现。问题不在“漏了哪一类”，而在**把四个不同维度塞进了同一个列表**：变更频率、产生方式、录入主体、审核要求，四件事被压成一条线，于是既会重叠，也必然漏。

四个维度分开之后，再补六类来源，分类才闭合。

另有一件事不属“来源”，但决定每条数据算谁的：**公司来自身份，不由表单选**。登录后即以任职公司为作用域，列表、新建、审核共用同一范围（第 5 节）。

混在一起的直接后果：

1. “不经常变更”会把主数据、规则参数、组织变更混成一类，而这三者的治理方式完全不同（停用 / 版本 / 生效日期）。
2. 只列“人工填”和“IoT”，会漏掉占比最大的一类：**系统派生**——运营总览、库存结存、产率、停机分钟，没有一个是填出来的。
3. 只列“事实数据”，会漏掉**计划/目标/预算**。运营已经有 `opsKpiTargets`，没有计划侧数据就没有“达成率”。
4. 只说“流转”和“审核”，没说清分段填写的三种形态，实现一定会走偏。

## 1. 原表述逐条核对

| 原说法 | 判定 | 需要修正或补充 |
| --- | --- | --- |
| 1. 不经常变更的数据，管理员或不同管理员共同维护（组织架构、人力部分数据） | 部分成立 | “不常变”不是判据，只是现象。真正判据是“被长期引用、改错代价高、要保留历史”。组织架构会重组、岗位会撤销，靠**编码稳定 + 停用不删除 + 变更审计**治理，不靠“它不变”。另外要区分“不同管理员各管各的记录”和“同一条记录不同字段分段维护”，后者是字段级权限问题。 |
| 2. 每天/经常填写，经营类数据（人事、采购、生产） | 成立，但需再拆 | 拆成**交易事实**（班报、到货、领用、隐患、入转调离）和**计划目标**（排产、月度目标、预算、销售预测）。两者不能同表同流程：事实可冲销、要审核；计划可调整、要版本。另，“人事”多数不是高频：入转调离是低频事件，高频的是排班、加班、考勤。 |
| 3. 其他模块流转（采购入库由采购清单流转） | 成立，但“流转≠复制” | 准确表述：上游单据**生成**下游单据，下游只继承标识和必要默认值，数量金额以本环节实际为准。本项目已有实例：采购清单 → 收货单，收货要同时填“实称吨数（计价）”和“实收张数（入库）”，与参考计量偏差超出所配允差即直接拒绝（`SUPPLY_REFERENCE_VARIANCE_EXCEEDED`，系统默认 3%）。必须支持部分到货、超收/短收、退货、改单、作废，以及“下游已生成后上游不能随意改”。 |
| 4. A 填一段 → B → C，部分需审核 | 成立，但必须先分三种 | (a) **字段级分段**：同一张单，A 填 A 段，提交后锁 A 段，B 填 B 段，需要字段权限 + 阶段状态机；(b) **单据接力**：A 的单生成 B 的单（报检 → 验收 → 入库），每张单各自审核；(c) **多级审批**：一张单提交后走 1–5 级、或签/会签，最后一级通过才生效——人事办理已按此实现，含审批人快照、逐级退回、发起人撤回、轮次 +1。三者实现方式完全不同，不能笼统说“经过审核”。 |
| 5. 物联网直采，不需要填写入口 | 方向对，“零入口”不成立 | 设备数据至少需要人工入口做四件事：设备与点位主数据维护、断线补录、异常确认（超阈值/跳变/停机原因）、口径校准（班次切分、计量单位）。本项目 PLC 已采集，排放在线监测尚未接；地磅属于“设备读数 + 人工清点”双来源，不是纯设备。 |

## 2. 四个正交维度

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| A 产生方式 | 人工录入 / 批量导入 / 单据流转 / 设备采集 / 外部接口 / 系统计算 / 历史迁移 | 数据“怎么进来的”，决定入口形态与校验位置 |
| B 数据性质 | 主数据 / 规则参数 / 交易事实 / 计划目标 / 派生快照 | 数据“是什么”，决定能否改、怎么改 |
| C 协同方式 | 单人 / 字段分段 / 单据接力 / 多级审批 / 跨组织同一记录 | 数据“谁填、几段”，决定权限与状态机 |
| D 治理要求 | 生效时点 / 审核级数 / 更正方式 / 留痕 / 会计期间 | 数据“怎么被信任”，决定流程与审计 |

正交的意思是每条记录同时有四个坐标，而不是被分到某一类里。例：

- 班报 = 人工录入 + 交易事实 + 班组单人 + 当日生效、可冲销
- 收货单 = 单据流转 + 交易事实 + 收货/质检两段 + 过账后才进统计
- 组织单元 = 人工录入 + 主数据 + 管理员 + 停用不删除
- 运营总览指标 = 系统计算 + 派生快照 + 无人 + 可重算、口径需版本

## 5. 入口范围：公司来自身份，不由表单选

登录即确定“我以哪家公司的身份操作”，此后列表、详情、新建、审批都继承同一范围。**公司是上下文，不是单据上的可编辑字段。**

链路不可跳步：

```
账号 → 员工档案任职（人 + 公司 + 岗位）→ 岗位映射权限集 → 权限集的 data scope → 可写公司集合
```

- **岗位不是公司来源。** 岗位回答“能不能做这件事”，公司来自任职。集团岗、共享岗、兼岗都不能靠岗位反推公司；`.agents/rules/architecture.md` 原文：“岗位不是租户边界：跨公司可见范围仍由权限集里的 data scope 决定”。
- **公司不是字段，是作用域。** 新建、编辑、列表、详情共用 URL 上的 `subjectId`；换公司等于换上下文并重载页面，不是把某个字段从 A 改成 B。
- **单公司账号**：表单里不出现公司下拉，页头只显示只读的“当前公司”。
- **多公司（兼岗/集团）**：允许切换，入口在顶栏；表单内不切换，有未保存内容先确认。
- **编辑态公司恒只读**，不依赖“是否已有明细/是否已提交”这类条件。
- **代录必须显式**：代谁、谁批准、留痕，不混在普通下拉里。

下级维度仍要选、仍需服务端校验：需求人、使用单元、供应商、物料、项目、仓库、产线都必须在公司范围内选，归属校验放服务端，前端过滤只算提示。

录入口径 ≠ 查看口径：审批人与集团角色按授权范围跨公司查看，不跟随录入人的公司过滤；`canWrite` 与 `readAll` 是两套规则。

### 5.2 与来源分类的关系

同一张表在不同公司可以是不同来源：项目公司 A 的采购申请由本地录入，项目公司 B 的由集团代录，来源字段 `onBehalfOf` 必须记代录对象。因此**来源矩阵（第 4 节）要按公司分解，不能全集团只写一行**；自动化率、代录比例这类统计也要能按公司切开。

## 6. 每条业务记录应带的来源字段

| 字段 | 取值/类型 | 说明 |
| --- | --- | --- |
| `sourceChannel` | `manual` / `import` / `flow` / `device` / `api` / `calc` / `migration` | 数据从哪来，用于统计“自动化率”和排查 |
| `sourceRef` | 单号/设备点位/批次/外部单号 | 能一路追回原始凭证 |
| `sourceDoc` | 附件 | 纸质、照片、扫描件 |
| `enteredBy` / `enteredAt` / `onBehalfOf` | 账号 + 时间 | 代录必须记代录对象，不能算成当事人自己填 |
| `businessDate` / `period` | 日期 / 期间 | 业务发生日与会计期间分开，跨期补录可识别 |
| `approvalState` / `reviewRound` | 状态 / 轮次 | 已退回重提的单据要能区分轮次 |
| `correctionOf` / `version` | 原单 ID / 版本号 | 更正单、冲销单指回原单，不改历史 |
| `dataOwner` | 组织或岗位 | 业务归属，不等于录入人 |

原则：**一条事实只有一个权威来源（system of record）**，其他来源只做核对，不并列展示两个“都对”的数。

## 7. 冲突、更正与时点规则

1. **多来源冲突**：确定主来源，设允差，超差阻断并留人工复核记录。地磅吨数与清点张数已是此模式（偏差超出所配允差即拒绝并提示复核，系统默认 3%）。
2. **交易数据不覆盖**：错单走冲销/红字/更正单，保留原单；只有过账数据进统计。现有“发货/到货只统计已过账”应作为全模块通用规则。
3. **主数据停用不删除**，改名不改 ID；被引用对象不允许物理删除。
4. **配置改动不影响在途单据**：提交时生成快照。人事审批链已如此，其他配置（审批链、计费规则、考核口径）照此办理。
5. **业务日期与录入日期分离**；月结后补录需单独授权并打标。
6. **设备断线**允许人工补录，标记 `device_gap`，恢复后对账；不能因为“设备没数”就让整条业务链停摆。
7. **派生数据可重算，但对外报表要留快照**，否则口径一变历史不可解释。

## 9. 借鉴与取舍：学什么、不学什么

取舍原则：**学约束，不学体量。** 判断标准三条——能靠数据库约束解决的，不建平台；能用一张表解决的，不建一个模块；能被现有审批链覆盖的，不上工作流引擎。

### 9.1 要吸收的（按落地成本从低到高）

| # | 做法 | 大厂怎么做 | 我们的缺口 | 落地方式 | 成本 |
| --- | --- | --- | --- | --- | --- |
| 1 | 已过账禁止编辑 | 系统里根本没有“修改已过账凭证”这个动作 | 各模块自己判断，有的只在前端隐藏按钮 | 平台级校验：过账/审核后写操作一律拒绝，错误码统一 | 低 |
| 2 | 统一单据关联 | 一张通用关联表记所有上下游（凭证流） | 每个模块各存 `sourceDocumentId`，跨模块追不动 | 新表 `document_links(source_type, source_id, target_type, target_id, company_id, created_at)`；写入时登记，详情页通用“上下游” | 低 |
| 3 | 期间与关账 | 会计期间 + 关账，关了记不进去 | 只有“已过账”，没有期间概念 | `period_locks(company_id, period, status)` + 过账校验；先只做月结锁账，不做多级关账 | 中 |
| 4 | 字段阶段锁定 | 字段状态控制，按阶段/角色决定可编辑字段 | 靠前端隐藏，后端不拦（如 `companyLocked`） | 分段状态 + 字段归属段，后端校验；不做字段级矩阵 | 中 |
| 5 | 配置带生效日期 | 配置表 + 生效期 + 提交时快照 | 审批链有快照，其他配置没有生效期 | 配置表加 `valid_from/to`，提交时快照 | 中 |
| 6 | 变更留痕 | 每个字段改动留一条（CDHDR/CDPOS 式） | 部分单据有版本记录 | 一张 `change_log`，只对关键单据启用，不做全量 | 中 |
| 7 | 主数据治理 | 去重、校验、审批、停用 | 编码唯一、停用不删已有；缺引用检查与去重 | 引用检查 + 唯一约束 + 停用前查引用；不上 MDG | 低 |
| 8 | 接口幂等与对账 | IDoc/中间件 + 监控重试 + 对账 | 尚未接财务等外部系统 | 外部单号唯一 + 对账表；接的时候再做 | 待接口时 |

### 9.2 明确不学的

| 做法 | 为什么不适用 | 我们的替代 |
| --- | --- | --- |
| 传输请求 / 多环境迁移体系 | 单体应用 + 迁移脚本 + git 已足够；建三套环境的成本高于收益 | 迁移脚本进版本库，按环境执行 |
| 多账套、平行准则、多币种 | 单集团单本位币，暂无跨境核算 | 科目表预留准则字段，不建第二套账 |
| 行业包 / 最佳实践流程库 | 流程是现场定的，套模板只会返工 | 按模块十问逐条确认 |
| 复杂条件技术（定价、税、折扣矩阵） | 规则数量不到需要矩阵的程度 | 价格表 + 手工覆盖 + 审批 |
| 字段状态全量矩阵 | 字段 × 事务 × 角色，配置量巨大，维护不起 | 段级锁定，字段按段归属 |
| BPM 工作流引擎 | 1–5 级审批、或签会签已覆盖 | 现有审批链 |
| 主数据治理平台（MDG） | 体量与数据量都不需要 | 约束 + 审批 + 停用 |
| 全量字段级审计 | 存储与性能成本高，绝大多数字段没人查 | 关键单据 + 关键字段 |

### 9.3 建议顺序

1. **先做 1、2、7**（低成本的约束类）：过账后禁改、统一单据关联、主数据引用检查。这三件不改流程，只加护栏，能立刻拦住最常见的错。
2. **再做 3、5**（期间与配置）：月结锁账 + 配置生效期。必须排在财务模块之前，否则财务一上线就得返工。
3. **最后做 4、6**（阶段与留痕）：字段分段锁定、关键单据变更日志。依赖前面的状态机，先做会反复改。
4. **8 等接口立项再做**，不要提前建。

判断是否想清楚了：每件都应当能用“一处迁移 + 一处校验”描述完。说不清，就说明设计过头了。

## 10. 支撑约定：维护、留存、异常、质量与边界

前面九节讲“数据该怎么来”，这一节讲“这套规矩怎么活下去”。

### 10.1 谁维护这份文档

- **责任岗位**：数据治理负责人（待指定）。在第 4 节矩阵补出“责任”列之前，暂由各模块开发负责人代行。
- **变更方式**：改文档必须同时递增标题行版本号；涉及矩阵或规则的改动，在文末变更记录加一行。
- **评审节奏**：按治理负责人定的周期评审；任何新模块上线前，先更新第 4 节，再上线。
- **失效判定**：超过约定评审周期仍未评审，文档标记为“待复核”，不得再作为验收依据。
- **与代码冲突**：以代码为准，两周内改文档；如果代码是错的，先开修复单，不允许只改文档把问题抹平。

### 10.2 保留与销毁

原则是**能说清“为什么还留着”，才允许留**；说不清，就到期处理。表中数字仅为示例，实际期限由管理员会同财务、法务确认后配置，文档不以这些数字作为标准。

| 数据类型 | 保留期（示例） | 到期处理 | 约束 |
| --- | --- | --- | --- |
| 已过账单据 | 10 年 | 归档只读，不可改 | 会计档案要求 |
| 未过账单据与草稿 | 1 年 | 删除 | 审批中的不删 |
| 审批与操作日志 | 5 年 | 归档 | 与单据分离存储 |
| 附件（合同、发票、证照） | 随所属单据 | 随单据归档 | 单独删附件须留操作记录 |
| 未引用附件（草稿期） | 7 天 | 删除 | 只清从未挂上任何单据的 |
| 个人信息（身份证、联系方式、银行卡） | 离职后 1 年 | 脱敏或删除 | 最小化收集 |
| 设备原始读数 | 2 年 | 降采样保留小时均值 | 存储成本 |
| 导入批次与失败行 | 2 年 | 删除 | 批次号保留即可 |

没有期限的数据，等于默认永久保留。永久保留的代价不是硬盘，是出事时解释不清。

### 10.3 异常场景

| 场景 | 现状 | 约定 |
| --- | --- | --- |
| 审批人离职或停用 | 任务可能永久卡住 | 按审批链顺序取下一有效审批人；无人可接则退回发起人；转交写入审批时间线 |
| 组织调整（合并、改名） | 业务单据只存 ID，名称实时取，历史显示新名 | 提交时快照组织名称；目前只有物料、供应商做了快照，组织尚未做 |
| 公司划转（主体变更） | 未定义 | 划转日前单据留在原主体，划转日后新开；跨主体查询需显式授权并留痕 |
| 设备长期断线 | 数据静默缺失 | 超过阈值标记 gap，人工补录并与产量、能耗对账；不允许静默跳过 |
| 单据长期停在中间态 | 占号、占额度 | 超过 SLA 提醒；可撤回重提，不允许直接改状态 |
| 账号更换或重名 | 归属可能错乱 | 以员工 ID 为准；账号可换，归属不变 |

这六种情况不会天天发生，但每一种都会在没人负责时变成“历史遗留问题”。

### 10.4 质量指标

规则定了没人看，等于没定。下面是五个起步指标，出数周期与触发阈值由管理员设定，文档只定“看什么、谁看”。

| 指标 | 定义 | 谁看 | 出数周期 | 触发复盘（阈值由管理员定） |
| --- | --- | --- | --- | --- |
| 允差超限率 | 超出物料所配允差被拒的收货单 / 收货单总数 | 采购 | 按配置 | 超阈值 |
| 代录比例 | 带代录标记的单据 / 总单据 | 各模块 | 按配置 | 超阈值 |
| 断线补录率 | 标记 gap 的时段 / 应采时段 | 生产、安环 | 按配置 | 连续多个周期上升 |
| 复核退回率 | 被退回次数 / 提交次数 | 各模块 | 按配置 | 超阈值 |
| 跨期补录数 | 业务日期早于当前期间的过账单据 | 财务 | 月结 | 逐笔审批 |

指标本身也要有责任人，否则就是第二份没人看的报表。

### 10.5 三处边界判定

| 边界 | 判据 | 后果 |
| --- | --- | --- |
| 附件 vs 事实 | 附件是证据，不进任何统计；金额、数量以结构化记录为准 | 统计只读结构化字段，附件只用于核对与举证 |
| 价格表 vs 规则参数 | 价格表是主数据：有编码、被引用、停用不删；规则参数是配置：审批链、允差 | 调价走版本不覆盖；改参数对在途单据用提交时快照 |
| 库存结存 vs 过账明细 | 明细是事实，结存是派生，可随时重算 | 对外报表留结存快照，内部对账一律回溯明细 |

一句话记法：**证据不计数，主数据不覆盖，结存只对报表负责。**

### 11.1 落地要点

**第 1 条**：复杂度全部压在写入侧。调岗走“新增 + 关闭”，历史记录自然保留；读接口只按当前时间过滤，不加 `asOf` 参数，避免所有查询都被穿透。

**第 2 条**：接力时整单交接，交出去的那一段字段锁死，接手人只能填后续段。这就是第 9 节第 4 条“段级字段锁定”的第一个用例。字段级分段等第二个场景（如供应商准入：采购填商务、财务填税务、法务填合同）再上。

**第 3 条**：现在连财务页面都没有，接口无对端。唯一要留的后手是导出：集团月报如果等不及，就先导出对账文件，不做实时回写。

**第 4 条**：阈值不写死在代码里。系统已有 `material.variancePercent`（默认 3，管理员可改，收货时快照到 `variancePercentSnapshot`），本来就该按物料维护——砂石带水，误差本来就大；钢材精密，差一点就该问。要加的是第二档：自动确认线与允差的比例由管理员配置，特殊物料可单独覆盖。三档为“自动确认 / 人工确认 / 拒收”，判断都用同一个物料配置，不引入全局常量。定期看每个物料的偏差分布：中位数若逼近自动确认线，说明秤或皮重有系统性偏差，查设备，不要调阈值。

**第 5 条**：两个特殊情况必须支持——草稿阶段附件先于单据存在（允许暂时无归属；超过保留期即清理，期限由管理员配置；只清从未被引用的）；一张发票对应多张入库单（关联表多行）。

**第 6 条**：默认主职是为了避免登录后落在冷门公司；切换必须显式，且切换后整页重载、清空未保存内容。改 `currentCompanyForUser` 时两处必须同时改，只改一处仍会出现“能选不能写”。

**第 7 条**：代码里 `stockDocuments` 的免批是写死的（`server/providers/warehouse-service.ts:41` 的 `controlled` 集合）：不在集合里的单据不能提交审批，只能从草稿过账。出库免批确认后，这段代码不动；要做的是把免批清单登记在 §4 矩阵的治理重点里，并在模块核对文件里保留代码位置。

### 11.2 一并明确的口径

1. **允差阈值按物料配置，不写死。** 它属于“规则参数”，归管理员维护，不归开发。砂石带水分、误差本来就大，钢材精密、差一点就要问，用一个全局百分比只会两头不讨好。配置项挂在物料上，有生效日期、提交时快照——改阈值不影响已提交的在途单据。
2. **孤儿附件按保留期清理，期限由管理员配置。** 期限太短只够当天填当天交；现场常常拍完照没信号、第二天回办公室才补。附件不大，多留几天成本可以忽略，误删的代价是重跑现场。只清从未被任何单据引用过的附件，一旦挂上单据即永久随单据。
3. **兼岗权限按第二家的任职岗位算。** 不是“与主职等同”，也不是笼统降权——你在第二家是什么岗位，就按那个岗位的权限集算；没有岗位映射的任职（只挂员工关系），默认只读。权限来自岗位，不来自人。
