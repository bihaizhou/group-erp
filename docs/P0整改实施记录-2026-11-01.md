## 2. P0-1 生产纠错闭环

### 2.1 原问题

- 班报确认先写产出快照、再改状态，非事务；失败会留下孤儿产出。
- 班报确认后没有作废/重开入口，错单无法更正。
- 生产入库路由用 `randomUUID()` 作为仓库请求键，重试会再建一张草稿。
- 建仓库单与回写 `prdShiftReportOutputs.stockDocumentId` 分两步，回写失败会留下未关联草稿。
- 仓库单已过账后仍可尝试作废班报，造成账实不符。

### 2.2 实现

新增迁移 `database/main/migrations/202611010001_production_report_corrections.ts`，为 `prdShiftReports` 增加：

- `voidedBy`、`voidedAt`、`voidReason`
- `reopenedBy`、`reopenedAt`
- `correctionHistory`（JSON，保存每次作废时的班报、产出和关联仓库单快照）

采用“同一行作废后重开”，不删除记录、不新建红冲班报。原因是 `prdShiftReports` 已有 `unique(unitId, reportDate, shift)`，同槽新建会被唯一键挡住；同槽更正也更符合“一张班报一条业务事实”的现场习惯。

状态与动作：

- `draft`：可确认、可编辑；
- `confirmed`：可创建生产入库草稿；无有效关联入库单时可作废；
- `void`：只可重开；重开回到 `draft` 并保留 `correctionHistory`。

作废规则（`server/providers/production-service.ts` 的 `voidShiftReport`）：

1. 班报必须是 `confirmed`，版本匹配；
2. 任一产出已关联 `posted` 仓库单，拒绝（`INBOUND_ACTIVE`）；
3. 任一产出关联 `draft/pending/approved` 仓库单，拒绝（`INBOUND_ACTIVE`），要求先在仓库取消；
4. 仅当关联单全部为 `cancelled` 或没有关联单时允许；
5. 写快照、清空产出关联、状态置 `void`、版本递增。

重开规则（`reopenShiftReport`）：仅 `void` 可重开；清空 `voided*`、`confirmed*` 和产出快照关联，回到 `draft`，保留 `correctionHistory`。再次确认时重建产出快照。

事务与并发：

- `confirmShiftReport` 改为 `database.transaction`：先用条件更新 `{id, status:'draft', version}` 抢占并递增版本，再删除未关联的旧产出、重建本次选中产出；并发确认只有一个请求成功。
- `linkInbound` 改为事务，校验仓库单 `kind=productionReceipt`、同主体、状态允许，再回写产出关联。
- 入库请求键由 `reportId + version` 派生稳定 UUID（`productionInboundRequestKey`，sha256 后格式化为 v5 形状）。同一班报同一版本重试复用同一张仓库单；作废重开后版本变化，才会生成新单。
- 已存在同一关联单时，入库接口直接返回当前班报，不重复建单。

API：

- `POST /api/production/shift-reports/:id/void`，body `{ version, reason }`；
- `POST /api/production/shift-reports/:id/reopen`，body `{ version }`；
- 原 `POST /api/production/shift-reports/:id/inbound` 保持路径，内部改为幂等。

页面 `client/pages/production/shift-reports.tsx`：

- `confirmed` 且无有效入库单时显示“作废”，弹窗必填原因（≤500 字）；
- `void` 显示“重开”和作废原因；
- 已取消的入库单仍显示查看链接；
- 已过账/流转中的关联单不显示作废，并给出提示。

## 3. P0-3 离职账号生命周期

### 3.1 原问题

离职只结束用工和任职，不更新员工状态/账号，不回收角色与会话。拥有 `readAll` 的离职账号仍可读全部数据。

### 3.2 实现

`server/providers/people-service.ts`：

- `PeopleService` 注入 `PermissionSetsApi<DatabaseConnection>`，由 `server/providers/people.ts` 传入 `authorizationToken.permissionSets`。
- `deactivateAccount(c, person)`：在事务内遍历该账号的直接权限分配，跳过 `protection.unrestricted` 和 `requireActiveAssignment` 的角色，其余撤销；捕获“最后一个角色”错误继续；最后 `users.withConnection(c).disable(accountId)`，内部撤销会话。
- `closeEmployee(c, person, actor, reason)`：先停账号，再把 `personnelEmployees.status` 置 `inactive`、`accountId=null`、`data.accountId=null`、`revision+1`；条件更新防并发；写 `exit` 审计。
- 离职分支先关闭全部 current assignments，再关闭 current employments，最后 `closeEmployee`；修正了原先按 `positionId` 误选表的问题。

保留 protected/root 角色不摘除，只禁用账号，避免把最后一个管理员锁死。这是有意的安全取舍。

### 3.3 测试

`tests/logic/people.test.ts` 9/9 通过，其中新增用例：建账号 + `personnel-reader` 角色 + 入职 + 离职，断言员工 `inactive`、`accountId=null`、账号 disabled、角色清空、旧会话 401。

### 3.4 仍存在的边界

- 没有“重新入职/恢复账号”流程；恢复需要管理员新建或重新启用账号并重新授权。
- 没有 HR 合同、请假、考勤、薪酬模块；离职只覆盖账号与任职生命周期。
- 兼职只建 assignment、不建第二 employment 的旧限制未在本轮扩展。

## 4. P0-4 安环闭环

### 4.1 原问题

- 事件只有列表/新建，没有调查、整改、关闭页面；
- 证照只有列表/新建，没有续期、吊销、恢复；
- 隐患 `PATCH` 任意状态，关闭时默认 `verifiedBy=当前人`，可自审；
- `approve` 权限已定义但路由未使用；
- 没有办理历史，只有 `version/updatedBy`。

### 4.2 迁移

`database/main/migrations/202611010002_hse_lifecycle.ts`：

- `hseIncidents`：`history` JSON；
- `hseHazards`：`history`、`rectifiedBy`、`rectifiedAt`；
- `hseCertificates`：`history`、`revokedBy`、`revokedAt`、`revokedReason`。

均 nullable；down 显式逐字段删除。

### 4.3 状态机与权限

事件 `reported → investigating → rectifying → closed`：

- `investigate`、`rectify` 需要 `manage`；
- `close` 需要 `approve`；
- 关闭必须有 `rootCause` 和 `actions`；
- `closed` 后禁止再流转，普通编辑也不再接受 `status`。

隐患 `open → rectifying → verifying → closed`：

- `startRectification`、`submitVerification` 需要 `manage`；
- `verify`、`return` 需要 `approve`；
- 提交验收必须有整改措施，并记录 `rectifiedBy/At`；
- 验收人不能等于整改提交人（含旧数据用 `updatedBy` 兜底），否则 `SELF_VERIFICATION`；
- `return` 必须填原因，退回 `rectifying` 并清空整改人，便于重新提交；
- `verifying/closed` 状态锁定普通编辑。

证照：

- `renew` 需要 `manage`，新到期日必须晚于当前到期日；
- `revoke`、`reinstate` 需要 `approve`；
- 续期后置 `active`；吊销写原因；恢复置 `active`；
- 列表状态仍按到期日动态派生 `expiring/expired`，不把派生状态写回库。

每次流转都追加 `history`（动作、from/to、办理人、时间、备注），并做 `version` 条件更新，冲突返回 409。

API：

- `POST /api/hse/incidents/:id/transitions`
- `POST /api/hse/hazards/:id/transitions`
- `POST /api/hse/certificates/:id/transitions`

三个接口分别返回更新后的记录；`options` 返回 `permissions.manage/approve`，页面据此显示动作。

### 4.4 页面

- `client/pages/hse/incidents.tsx`：调查/整改/关闭动作弹窗，原因与措施必填，显示最近办理；
- `client/pages/hse/hazards.tsx`：开始整改/提交验收/验收关闭/退回整改，提交验收时填写整改措施，退回必填原因；
- `client/pages/hse/certificates.tsx`：续期（日期+说明）、吊销（说明）、恢复（说明）；
- 中英文案补齐；`hse.action.*` 与字段文案统一走 locale。

### 4.5 测试与文档

- `tests/logic/hse.test.ts`：覆盖事件完整流转、经理无 `approve` 不能关闭、审批人关闭、隐患自审 400、独立审批人验收、退回再提交、证照续期/吊销/恢复、关闭事件不可再改、未声明路由检查、只读用户 403。
- `tests/logic/hse-lifecycle-migration.test.ts`：up/down/up 与字段断言。
- 结果：HSE 1/1、迁移 1/1 通过；定向 eslint 通过；typecheck 通过。

### 4.6 仍存在的边界

- `hseInspections`、`hseWorkPermits`、`hseTrainingRecords`、`hseActions` 仍只有表和权限登记，没有 API/页面；本轮未做检查、作业票、培训、措施跟踪。
- 生产维修与作业票仍无强制校验；`hseWorkPermits.linkedMaintenanceOrderId` 是无外键的普通字段。
- 没有到期提醒定时任务/通知；证照到期只在查询时计算。
- 办理历史是 JSON，不是独立事件表；跨记录检索能力有限。

## 5. P1a 生产投入行

### 5.1 落地范围

按 [P0-2 设计](P0-2-生产投入与经营闭环设计.md) 的第一阶段，班报从“只记产出”补到“产出 + 投入”。投入行是**消耗事实**，不直接改库存；库存仍只能由领用出库/生产领用单过账。

新增迁移 `database/main/migrations/202611010003_production_report_inputs.ts`，创建 `prdShiftReportInputs`：

| 字段                                   | 说明                                 |
| -------------------------------------- | ------------------------------------ |
| `id, subjectId, reportId`              | 主键、主体、所属班报                 |
| `skuId, quantity, unitId, unit`        | 投入物料、数量、单位及单位快照       |
| `sourceType`                           | `manual` 手工 / `issue` 关联领用出库 |
| `issueRequestId, issueRequestLineId`   | 关联领用申请及行                     |
| `stockDocumentId, stockDocumentLineId` | 关联出库单及行                       |
| `note, version, audit`                 | 备注、乐观锁、审计                   |

约束与索引：

- `unique(reportId, stockDocumentLineId)` 防止同一出库行重复挂到同一班报；
- `unique(id, reportId, subjectId)` 供复合外键引用；
- 对 `reportId`、`(issueRequestId, issueRequestLineId)`、`(stockDocumentId, stockDocumentLineId)` 建索引；
- 删除班报时级联删除投入行。

### 5.2 服务端规则

- 只有 `draft` 班报可增删改投入；`confirmed/void` 只读；
- 物料必须属于当前主体且为 `active`，数量 > 0、最多 6 位小数，单位取 SKU 基本单位并做快照；
- 手工行必须填写备注，说明来源或估算依据；
- 领用关联必须同时给 `issueRequestId + issueRequestLineId + stockDocumentId + stockDocumentLineId`，服务端校验四者在同主体、领用行属于该申请、出库行属于该申请/出库单且状态为 `posted`，数量不得超过出库行数量；
- 关联行不允许删除或改数量/物料，只能改备注；需要更正时先作废班报、由仓库处理单据后重开；
- 班报确认时至少一行投入，否则 `SHIFT_REPORT_INPUT_REQUIRED`；确认/作废/重开的历史快照都带投入行，重开后保留可编辑投入。

API：

- `GET /api/production/shift-report-inputs/options`：返回可用物料、已过账领用出库单及行；
- `POST /api/production/shift-reports/:id/inputs`：新增；
- `PATCH /api/production/shift-reports/:id/inputs/:inputId`：改数量/备注；
- `DELETE /api/production/shift-reports/:id/inputs/:inputId`：删除手工行。

### 5.3 页面

`client/pages/production/shift-reports.tsx` 新增“投入”操作和明细弹窗：draft 可新增手工/领用投入、删除手工行；列表展示投入行数，详情展示物料、数量、单位、来源和关联出库单。中英文案已补齐。

### 5.4 测试与验证

- `tests/logic/production-report-inputs-migration.test.ts`：建表、字段、up/down/up；
- `tests/logic/production-full-chain.test.ts`：手工投入、领用投入、超领用数量拒绝、关联行删除 409、确认后投入快照、入库幂等；
- 结果：上述测试通过；typecheck、定向 eslint 通过。

### 5.5 仍存在的边界

- 没有 BOM/配方、消耗定额、自动倒冲；投入是人工登记或领用单关联；
- 领用行没有“已消耗数量”累计，同一出库行可挂到多张班报；跨班报的消耗上限要在成本/领用核销阶段补；
- 投入行不生成库存流水，也不计算成本；成本仍在 P2a；
- 没有“无投入原因”参数，当前统一要求至少一行投入；
- 生产计划仍未建，投入无法按计划/工单归集。

## 9. 进销存责任链与固定资产补强（2026-10-22）

针对“入库、出库、进销存、谁领的、谁名下有哪些固定资产”的专项核查，补充以下闭环。

### 9.1 采购收货拒收数量

- `stockDocumentLines` 新增 `baseRejectedQuantity`，与 `baseQuantity` 一起冻结收货数量；`baseQuantity` 表示合格入库数量，拒收数量不再进入库存和订单已收数量。
- 迁移：`202611010004_purchase_receipt_rejections.ts`。
- 采购入库、采购退货上限、订单履行回写和冲销均以合格数量为准；超量校验改为“合格 + 拒收 ≤ 订单剩余”。
- 测试固化：收 6 拒 1 时库存增加 5、订单已收 5，不再出现“拒收仍入库”的旧行为。

### 9.2 领用出库与签收
