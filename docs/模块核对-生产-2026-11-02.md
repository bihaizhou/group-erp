# 模块核对 · 生产（第三位）

v0.1 · 2026-11-02 · 依据《数据来源分类与治理约定》v1.5（下称“总纲”）
核对范围：`client/pages/production/`；`server/providers/production-model.ts`、`production-service.ts`；`server/routes/production.ts`；迁移 `202610240001`–`202611010010`
核对表：`prdUnitProfiles`、`prdOutputMappings`、`prdSchedules`、`prdScheduleAssignments`、`prdAttendanceRecords`、`prdShiftReports`、`prdShiftReportOutputs`、`prdShiftReportInputs`、`prdDowntimeEvents`、`prdOvertimeRequests`、`prdEquipment`、`prdMaintenanceOrders`、`prdMaintenancePlans`

## 0. 结论

- **班报是全模块的账本。** 确认后的班报产出两张快照：产量（金属/砂）与物料消耗。入库单由班报一键生成，但只是草稿，要仓库过账后才算库存。生产确认数量、仓库确认实物，这个两段式是对的。
- **但班报没有审批。** “确认”就是有 `manage` 权限的人点一下（`production-service.ts:2256`），填表人和确认人可以是同一个。改错只能作废重开，没有第二个人看过。
- **停机分钟是手填的。** 停机事件表 `prdDowntimeEvents` 单独记，班报里的 `downtimeMinutes` 既不从它汇总，也不与它核对。同一个班次，两边可以给出两个数。
- **“设备直采”在平台侧有、在 ERP 侧没有。** 集团 PLC 采集链路已跑通（现场 Node-RED → 公网 MQTT → ClickHouse / FUXA，见仓库根目录《PLC 数据采集与总部监控阶段总结》），但哈尔滨只登记了 `gateway_online`，真实测点未接；`group-erp` 里也没有任何代码去采集服务取数，`prdUnitProfiles` 的 `gatewayKey`、`fuxaPageKey`（`production-model.ts:251`、`:252`）只是两个文本字段。生产数据目前全部靠人填。
- **排班发布不留痕。** `publishedBy`、`publishedAt` 两列建了但从不写入；已发布的排班再保存一次，会退回草稿并把人员清空重选。

## 1. 来源清单

### 1.1 主数据

| 对象 | 来源 | 权威表 | 谁维护 | 快照位置 | 备注 |

| 单元 / 产线档案 | 手工建档 | `prdUnitProfiles` | 生产管理员 | — | `subjectId` + `unitId` 唯一；含设计产能 `designCapacityTpd`、投产日、区域、网关键（`gatewayKey` 只是文本，ERP 未用它取数） |
| 产量映射 | 手工建档 | `prdOutputMappings` | 生产管理员 | 班报确认时写 `prdShiftReportOutputs.skuId` | 金属、砂各一行，指定默认仓库；缺映射时确认被拒 `OUTPUT_MAPPING_MISSING` |
| 设备 | 手工建档 | `prdEquipment` | 设备管理员 | 维修单 `equipmentId` | 有 `criticality`、`status`（active / maintenance / retired） |
| 保养计划 | 手工建档 | `prdMaintenancePlans` | 设备管理员 | 工单 `planId` | 按 `intervalDays` 生成到期工单；完成时回写 `nextDueOn` |
| 班次 | 常量 | 代码内 `productionShifts = ['day','night']` | 不可维护 | — | 固定白/夜两班，没有第三班与跨零点定义 |
| 人员与岗位 | 人事档案 | `personnelAssignments`、`orgPositions` | 人事 | 出勤、排班存 `personId` + `positionId` | 班报只存单元，不存人；人只在出勤与排班里 |

### 1.2 班报（`prdShiftReports`）

表头：`subjectId`、`unitId`、`reportDate`、`shift`、`status`、`processedQuantity`、`metalQuantity`、`sandQuantity`、`tailingsQuantity`、`runtimeMinutes`、`downtimeMinutes`、`notes`、`confirmedBy/confirmedAt`、`voidedBy/voidedAt/voidReason`、`reopenedBy/reopenedAt`、`correctionHistory`、`version`。
唯一键：`unitId + reportDate + shift`，一个单元一天一班只能有一张。

明细两张：

| 表 | 内容 | 什么时候写 |
| --- | --- | --- |
| `prdShiftReportOutputs` | `outputType`（metal/sand）、`skuId`、`warehouseId`、`quantity`、`stockDocumentId` | 确认时按映射生成快照；`stockDocumentId` 在入库单生成后回填 |
| `prdShiftReportInputs` | `skuId`、`unit`、`quantity`、`sourceType`（manual/issue）、`issueRequestId`、`stockDocumentId`、`note` | 草稿期手工加；引用领用单时带 `sourceType='issue'` |

状态与动作：

```text
draft --确认(manage)--> confirmed --作废(manage, 需填理由)--> void --重开(manage)--> draft
```

- 确认做三件事：锁定 `confirmedBy/confirmedAt`、按映射生成产量快照、回填 `version`。**不生成库存单据，不动库存。**
- 入库要再走一步：`inboundDraft`（`production-service.ts:2515`）算出待入库行，前端调执行模块建 `productionReceipt` 草稿，再 `linkInbound`（同文件 `:2584`）回填 `stockDocumentId`。建单带 `productionInboundRequestKey(reportId, version)`，重复点击不会重复建单。
- 物料消耗若引用领用单，确认前会检查那张出库单必须已过账，否则 `INPUT_ISSUE_NOT_POSTED`。
- 作废要求关联入库单已取消，否则 `INBOUND_ACTIVE`；作废时把整张班报（含明细、产量、消耗）存进 `correctionHistory`，再删产量快照。
- 重开把单子退回 `draft`，`confirmedAt` 清空，产量快照删除，等下一次确认重新生成。

### 1.3 现场记录

| 对象 | 权威表 | 谁填 | 审核 | 更正方式 |
| --- | --- | --- | --- | --- |
| 出勤 | `prdAttendanceRecords` | 有 `manage` 的人按班填 | 无 | 直接改；同人同日同班只有一条，按存在则更新 |
| 停机 | `prdDowntimeEvents` | 现场报，`manage` 关单 | 无 | `open` 可关闭或取消，关闭时算时长；关闭后不可改 |
| 加班 | `prdOvertimeRequests` | 本人或代报 | 单级，`approve` 权限 | 驳回要写理由；通过后不可改 |
| 排班 | `prdSchedules` + `prdScheduleAssignments` | 生产管理员 | 无，发布即生效 | 再保存退回草稿并清空人员；发布不记录发布人 |
| 维修工单 | `prdMaintenanceOrders` | 设备管理员 | 无 | 状态只能前进：reported → in_progress → completed / cancelled；完成必须填 `solution` |

出勤名单的取数：当天有已发布排班就按排班的人，没有就按单元里的生产岗位取在岗人员（`production-service.ts:571` 起）。加班分钟必须挂在“出勤”或“休息”上，且必须写加班内容，否则 `OVERTIME_WITHOUT_PRESENCE` / `OVERTIME_CONTENT_REQUIRED`。

### 1.5 与库存的衔接

生产入库、生产领料在库存侧是两张 `stockDocuments`（`kind = productionReceipt / productionIssue`），属于仓库模块，不属于生产模块。生产这边只负责“数量从哪来”：入库来自班报确认后的产量快照，领料来自领用申请审批后的出库单。两张单都过账后，库存账才动。

## 5. 与采购、仓库试点的差异

- **没有公司下拉问题。** 生产页面以“单元”为入口，公司由单元带出，表单里不选公司。代价是 10 个页面里只有概览、日报声明了 `companyScope`（`client/pages/production/routes.ts:28`、`:37`），其余 8 个没有页面级公司上下文——与总纲 §5“公司是上下文”不完全一致，靠服务端按单元解析。暂不构成错误，但要登记。
- **没有接审批引擎。** 采购、仓库都走 `@nocobase/lifecycle` 的复核，生产没有；更正靠“作废 + 重开”，与总纲 §7.2 的冲销思路不同。申请类单据可以这样，事实类单据（班报）建议补更正单。
- **两段式确认值得保留。** 生产确认数量、仓库确认实物，中间用草稿入库单衔接，`requestKey` 幂等。这比“班报确认即入库”稳，也比“仓库自己填产量”可追。

## 6. 怎么复制到第四位（人力）

1. 先列这个模块的表，按“主数据 / 事实 / 计划 / 派生”四类分开，不要按页面分。
2. 每张事实表问三件事：谁填、谁确认、错了怎么改。三者缺一，就是差距。
3. 派生数据先确认“有没有落表”。落了表就要问“谁负责重算、什么时候重算”；没落表就写清算法在哪。
4. 跨模块引用只记“引用键 + 快照字段”，不要在本模块重复存对方的全量数据。
5. 最后才排优先级：先修“数会错”的，再修“错了改不动”的，最后修“看不出来源”的。
