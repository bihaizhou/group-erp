# 采购申请与审核配置后端实施记录

日期：2026-10-18（Phoenix）。状态：A2.2 后端首批已在本地实现，未部署；采购申请与审核配置页面后续已本地实现，见 [页面实施与验收](采购申请页面实施与验收.md)，整批 A2.2 尚未完成。供应商既有交付保持不变。搭建环境仍为 `materials-tags-20261018-043000`，本轮未连接、迁移或修改实际环境。

## 已实现

- 采购草稿、稳定行 ID、原始需求、已知 SKU 与未知需求混合保存；保存和提交在同一真实事务内重查公司、真实人员用工及部门任职、供应商资格、物料准入和精确单位包装。
- `draft → pending → approved`，以及退回、撤回、批准后修订、取消、取消后复制为关联新单。审批允许与未知物料识别并行；不创建治理任务，不记录订单、收货或库存发生数量。
- 独立的业务 `revision`、内容 `contentVersion`、生命周期 `lifecycleVersion`、治理有效期 `governanceEpoch` 和审核轮次。客户端必须同时携带业务和生命周期版本，旧决定、旧整单覆盖及跨单行 ID 被拒绝。
- 不可覆盖的提交内容快照和审核任务。退回或撤回后原快照保留，同内容重提复用内容快照并创建新轮次；修改内容产生新快照，旧批准只在历史中保留。
- 公司审核配置接入官方 `StoredLifecycleParameters` 六表；首次提交冻结规则，重提沿用原规则，每轮按当前有效任职重新解析候选。新规则用于新申请；需要换规则时取消旧单再复制。
- 官方审核选择器支持岗位和账号；同组取交集、不同组取并集。过滤停用账号、无有效用工或任职的账号，以及创建人、当前实际申请人、提报及代办账号。候选在本轮任务内固定，任一有效候选可作决定。所有旧候选失去资格后，独立的审核交接动作按原规则重新解析，保留旧任务和原因。
- 组织 → 供需 → 物料锁顺序。单头、明细、快照、规则使用事实、任务、官方生命周期日志、审计和动作重放共同提交或回滚。同键重试重查权限、行范围和读写字段，不重复建单或办理。

## 模型与迁移

新增不可变迁移 `202610180001_purchase_requests` 和增量 seed `202610180001_purchase_request_defaults`，没有编辑旧迁移或旧初始化。新增十张表：

| 集合                                                                      | 内容                                                           |
| ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `purchaseRequests`                                                        | 采购单头、独立版本、当前提交/批准引用、识别统计及经办身份      |
| `purchaseRequestLines`                                                    | 稳定明细身份、原始需求、明确数量单位、材料与包装快照、取消历史 |
| `supplyChainRequestVersions`                                              | 内容版本与提交快照                                             |
| `supplyChainReviewTasks`                                                  | 每轮固定候选、资格排除、决定、交接和关闭事实                   |
| `supplyChainParameterHeads/Versions/Selections/Requests/Snapshots/Usages` | 六张独立表，逐列遵循官方存储契约                               |

单头/主体组合唯一；明细与版本/任务的父单主体有组合外键，行号、内容版本、审核轮次有唯一约束。数量、非负版本和计数边界在数据库执行。`neededOn` 使用日期字段，按集团业务日期校验人员资格，不用浏览器时区决定业务日。

**官方数据库包的 CHECK 编译缺口已实测确认**：`@nocobase/db` beta.20 会跳过 DSL CHECK。新迁移对 PostgreSQL 使用真正的 CHECK，对 SQLite 使用 INSERT/UPDATE 约束触发器；仅此能力通过迁移事务的 driver 执行 DDL，物理标识从官方 Query 编译结果解析并严格校验。没有用一份被跳过的声明充当已生效的约束。其他表、索引和外键仍用官方 Builder。SQLite及后续PostgreSQL专项均已证明直接非法写入被拒绝，以及非空样例up/down/up正常；详见 [专项记录](采购A2.2隔离PostgreSQL验证.md)。

共享内容版本及任务表目前明确只承载采购，并约束到真实 `purchaseRequests`。A2.3 领用接入必须新增迁移扩展父单约束，不能直接把领用 ID 塞入采购外键或改写本迁移。参数六表可按服务端确定的模块/主体 scope 复用；现有供需锁、审计和重放表继续复用。

## API 与权限

路径均为 `/api/procurement` 下相对地址，不含部署前缀；所有接口独立认证、按业务动作授权，输入使用严格 schema，响应为 `{ data }` 或 `{ data, meta }`，并声明 OpenAPI。

| 接口                                                                        | 行为                                                         |
| --------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `GET/POST /requests`                                                        | 公司范围内搜索分页／原子创建草稿                             |
| `GET/PATCH /requests/{id}`                                                  | 完整详情／版本条件保存草稿                                   |
| `GET /requests/{id}/history`                                                | 按父单权限分页读取审计                                       |
| `POST /requests/{id}/submit/approve/return/withdraw/revise/cancel/reassign` | 七个分别命名的动作接口，每次重查权限和版本                   |
| `POST /requests/{id}/copy`                                                  | 仅取消单可复制；新单和新行身份，关联旧单，重新冻结规则       |
| `GET /requestCompanies`                                                     | 申请业务允许的公司选项                                       |
| `GET /requestOptions`                                                       | 按公司搜索最小人员／部门／岗位选项；普通申请人只获得本人选项 |
| `GET/PUT /settings`                                                         | 读取／按完整参数组、版本和请求键保存公司审核规则             |
| `GET /settings/companies`、`GET /settings/options`                          | 配置职责下的公司、岗位及有效审核账号选项                     |

申请资源 `procurement.requests` 区分 read/create/update/submit/review/withdraw/revise/cancel/reassign/delegate。审核配置为独立的 `procurement.settings.read/update`。页面权不替代这些动作；没有公开原始采购或参数集合写接口。

初始化新增五个可编辑职责模板：采购申请人（本人）、采购代办（本公司）、采购审核（本公司）、采购审核配置（本公司）、采购审核交接（本公司）。seed 在隔离应用中已执行和复验；**未应用到实际环境，未分配真实账号，没有预设公司或审核人**。实际人员由管理员配置，已存在的权限模板不被覆盖。

公司范围与本人范围同时受父单及公司策略控制。代办许可单独取得其公司范围，再对目标公司校验；不能把“在 A 公司可代办”放宽成主动作允许的所有公司。审核候选身份不自动产生业务审核权限。
