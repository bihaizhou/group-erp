## 0. 结论

- **人事的“账本”是异动单，不是员工表。** 入职、转正、调动、兼职、结束兼职、离职六类都走 `personnelChanges`：提交、审批、到生效日自动执行。员工表、劳动关系、任职是执行结果。
- **审批是真的多级。** 每种异动可单独配 1–5 级，每级可选“或签 / 会签”，审批人可按角色、指定账号、岗位三种方式指定，还能限定只对某几家公司生效。审批人名单在提交时快照进 `peopleApprovalTasks`，事后改配置不影响在途单。
- **但入口有两个。** 劳动关系、任职两张表在页面上仍有“新建 / 编辑”，服务端也没拦。只要权限够，可以不走异动直接建一条任职，没有审批、没有生效日、没有异动留痕。
- **员工档案先于入职存在。** 新员工一建档就是 `active`，没有“待入职”状态；入职异动只是补劳动关系和任职。档案里还能提前绑账号。
- **离职生效前只卡资产。** 有未归还资产不能生效（`PEOPLE_ASSETS_OUTSTANDING`）；交接清单可配，但不完成也能审批通过、也能生效。
- **没有合同到期提醒。** 合同结束日只是一个字段，改日期走一个单独动作并留审计；没有到期名单、没有续签流程。
- **附件只有照片。** `peopleFiles` 只服务员工头像（图片、5 MB 上限）；合同、学历、证书没有归档位置。

## 1. 来源清单

### 1.1 主数据

| 对象 | 来源 | 权威表 | 谁维护 | 备注 |
| --- | --- | --- | --- | --- |
| 公司、部门、岗位 | 组织模块 | `orgSubjects`、`orgUnits`、`orgPositions` | 组织管理员 | 人事只引用，不复制；岗位的 `reportsToId` 决定“上级评价”是谁 |
| 员工档案 | 手工建档 | `personnelEmployees` | 人事专员 | `code` 唯一；`status` 建档即 `active`；`subjectId` 归属公司；可绑 `accountId` |
| 人才卡 | 随员工自动生成 | `hrProfiles` | 人事 / 员工本人 | 建档时自动建一张空卡（`snapshot.generated`） |
| 能力维度 | 手工建档 | `hrDimensions` | 人事 | 五个等级标准必填；不挂公司 |
| 岗位能力模型 | 手工建档 | `hrModels` | 人事 | 挂岗位，公司由岗位带出；维度 1–24 个 |
| 敏感联系信息 | 手工录入 | `personnelPrivate` | 本人或人事 | 手机、邮箱单独存，单独权限，审计只记“改过”不记值 |
| 照片 | 上传 | `peopleFiles` | 本人或人事 | 仅图片，5 MB；上传需员工 `update` 权限 |

### 1.2 异动单（`personnelChanges`）

表头：`code`（`CHG-YYYYMMDD-` + 4 位随机）、`personId`、`subjectId`、`status`、`reviewRound`、`createdBy`、`data`、`snapshot`。
`data` 关键字段：`type`（entry / transfer / partTime / endPartTime / exit / regularize）、`effectiveDate`、`targetSubjectId`、`targetPositionId`、`employmentId`、`assignmentId`、`changeEmployer`、`employmentType`、`probationEnd`、`contractEnd`、`location`、`explanation`（必填）。

状态：

```text
draft --提交--> pending --审批--> approved --到生效日(自动)--> effective(终态)
  |               |  |                |
  |               |  +--退回/撤回--> draft
  +---------------+------------------+--取消--> cancelled(终态)
```

- 提交时：`reviewRound + 1`、按类型生成交接清单、按公司过滤审批链、逐级建审批任务（第一级 `pending`，其余 `waiting`）。
- 审批通过：当前级记决定；或签一人即过，会签需全部候选人通过；过完进下一级；最后一级过完 → `approved`。
- 生效：`approved` 且 `effectiveDate <= 今天` 时，提交那一刻立即触发；未来日期由后台每 30 秒扫一次（`sweepEveryMs: 30000`），到期自动执行。生效动作不可人工点，`apply` 是非手工迁移。
- 生效做什么：入职建劳动关系 + 任职、把员工归属公司改到目标公司、人才卡与敏感信息跟着换公司；调动关闭原任职、开新任职，跨主体调动还换劳动关系；离职先查资产，再关任职、关劳动关系、停用账号、清空 `accountId`、员工置 `inactive`、人才卡置 `inactive`；转正只更新试用期结束日与 `regularizedAt`。

### 1.3 人事记录

### 1.4 人才与绩效

| 对象 | 来源 | 审批 | 说明 |

## 4. 责任与待定

**谁负责**

- 业务责任人：人事负责人（档案、异动、合同）、各公司负责人（编制确认）、部门负责人（绩效上级评价）。具体人名待定。
- 系统责任人：人力模块迁移、审批链配置、本文档同步；改审批链或加异动类型必须回来改本文第 1、2 节。

**待业务决定**

1. H2 是否关闭劳动关系/任职的直接入口？关了就只剩异动一条路。
2. 员工建档要不要“待入职”状态，账号什么时候能绑？H1。
3. 离职交接哪些项必须完成才能生效？H4。
4. 合同到期提前多少天提醒、由谁处理？H5。
5. 编制计划的公司确认人按什么定（公司负责人 / 人事负责人）？

**已成立、不需要再讨论的**

- 员工归属公司的直接修改，有劳动关系后一律拒绝（`PEOPLE_USE_CHANGE`），只能走异动。这条与总纲 §5 一致。
- 生效日不能提前执行（`PEOPLE_NOT_DUE`），未来日期由后台自动扫。这条与总纲 §6 一致。

## 5. 与前三位的差异

- **没有页面级公司上下文。** 采购、仓库、生产至少部分页面声明了 `companyScope`；人事 15 个页面一个都没有，全靠记录上的 `subjectId` 加数据权限过滤。集团 HR 跨公司看、公司 HR 只看本公司，取决于权限集配的 data scope。这与总纲 §5“公司是上下文”不完全一致，但不构成错误：人事本来就常由集团统管。登记在此，不当作差距。
- **审批链是配置出来的，不是写死的。** 采购、仓库的审批人配置也走同一引擎，但人事把“按异动类型分链、按公司限定、1–5 级、或签/会签”做全了。这是目前四个模块里最完整的一处。
- **生效是时间驱动的。** 采购、仓库、生产的单据都是“点了才算”，只有人事有“未来生效、到点自动执行”。这套 `effectiveDate` + 后台扫描的写法，后面组织调整、价格生效可以直接借。
- **更正靠反向异动，不靠改原单。** 与总纲 §7.2 一致，比生产班报的“作废重开”更干净。

## 6. 给第五位（组织）的提示

1. 人事这边对组织的依赖已经很清楚：岗位 `reportsToId` 缺失，绩效上级就评不了；岗位停用，审批人解析就落空。组织模块核对时，先把这两条当输入。
2. 组织自身的“生效日期”如果也做成未来生效，直接复用人事这套 `effectiveDate` + 扫描，不要再造一套。
3. 组织的编码、层级、公司归属变更，要问“历史单据里的组织快照还对不对”。人事的异动 `snapshot` 存了当时的公司/岗位名，组织改名不会回填——这是对的做法，组织核对时要确认其他模块也这样。
