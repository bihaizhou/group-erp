# 模块核对 · 平台公共与复核配置

v0.1 · 2026-11-02 · 依据《数据来源分类与治理约定》v1.8（下称“总纲”）
核对范围：`client/pages/settings/`（用户、角色、权限、默认权限）、`client/pages/auth/`、`client/pages/review-settings/`、`client/components/review-rule-editor.tsx`；`server/providers/execution-review-service.ts`、`execution-reviewers.ts`、`review-rule-fields.ts`、`review-scope.ts`；`node_modules/@nocobase/lifecycle/dist/parameter-configuration.js`
核对表：`users`、`roles`、`permissionSets`、`positionPermissionSets`、lifecycle 参数版本表（`versions` / `heads` / `requests` / `selections`）、`supplyChainFiles` / `supplyChainFileLinks`、`peopleFiles`

## 0. 结论

- **平台公共不是业务模块，是底座。** 账号、角色、权限集、数据范围来自 NocoBase 的授权插件；本仓库自己做的只有三件：岗位与权限集的绑定、按公司的复核人配置、各模块的审计页。
- **复核人配置是唯一“按公司存、带版本、带快照”的配置。** 采购、领用、仓库、销售各有一套页面，存的都是“这家公司这类单据由谁复核”；保存时校验每个选择、带版本号防并发、带操作人和请求号防重复提交；单据提交时把当时的配置整份快照进单据。
- **复核人解析很严，严到会挡住提交。** 候选人必须是本公司在职员工、有有效劳动关系、有有效任职、岗位在本公司有效部门下、账号未停用，还要排除申请人自己。一条都不满足就报错，不会退回给管理员兜底。
- **附件有两套。** 业务附件在 `supplyChainFiles` + `supplyChainFileLinks`；人事附件只有 `peopleFiles`（头像）。没有统一的附件中心。
- **审计是分散的。** 组织有 `orgAudit`，人事有 `peopleAudit` 与各单据时间线，物料、供应商有各自的履历页，单据有 lifecycle 迁移记录；没有跨模块的“某人某天改了什么”。
- **配置有版本，但页面不看历史。** 复核配置每次保存都会形成新版本，库里留着；页面上只显示当前版本号，没有“上一版是什么”的入口。

## 1. 来源清单

### 1.1 账号与权限

| 对象 | 来源 | 权威表 | 谁维护 | 备注 |
| --- | --- | --- | --- | --- |
| 账号 | 管理员创建，或注册 | NocoBase `users` | 系统管理员 | 人事离职会停用并清空员工上的 `accountId` |
| 角色 | 手工建 | NocoBase `roles` | 系统管理员 | 角色是权限的容器 |
| 权限集 | 手工建，挂资源动作与数据范围 | NocoBase 授权表 | 系统管理员 | 数据范围决定“能看哪些行” |
| 岗位与权限集绑定 | 组织模块的 `position-permissions` 页面 | `positionPermissionSets` | 组织管理员 | 这就是“岗位 → 权限集”那一环；改绑定不等于立刻改已登录会话 |
| 默认权限 | `settings/default-access` 页面 | NocoBase 授权表 | 系统管理员 | 新账号的兜底权限 |

### 1.2 复核人配置

| 项 | 现状 | 位置 |
| --- | --- | --- |
| 作用域 | `execution:<公司 id>` 或领用申请自己的 scope；按公司隔离 | `review-scope.ts`、`execution-review-service.ts:47` |
| 可配字段 | 只有两类：复核人选择（`reviewers`）和布尔开关（`boolean`，如并行治理） | `review-rule-fields.ts:8` |
| 选择方式 | 角色 / 指定账号 / 岗位，可组合成组；每组最多 100 个选择 | `parameter-configuration.js:123` |
| 保存 | 先逐组解析、再校验版本号（`expectedRevision`）、记 `actorId` 与 `requestId`（幂等） | `execution-review-service.ts:339-366` |
| 版本 | 每次保存生成新版本，旧版本留在库里 | `parameter-configuration.js:111-139` |
| 快照 | 提交时把整份配置写进单据的 `parameterSnapshot` | `execution-review-service.ts:223` |
| 候选人资格 | 本公司在职员工 + 有效劳动关系 + 有效任职 + 岗位在本公司有效部门 + 账号启用 + 排除申请人 | `execution-reviewers.ts:28-71` |
| 解析为空 | 直接拒绝提交（`STOCK_REVIEWERS_EMPTY`） | `execution-reviewers.ts:104-113` |

### 1.3 附件与审计

| 对象 | 表 / 入口 | 覆盖范围 |
| --- | --- | --- |
| 业务附件 | `supplyChainFiles`、`supplyChainFileLinks` | 采购、领用、销售、仓库存证；按 `versionKey` 区分当前版与提交版 |
| 人事附件 | `peopleFiles` | 只有头像，图片 5 MB |
| 组织审计 | `orgAudit` | 每次增改停用，含改前改后、操作人、理由 |
| 人事审计 | `peopleAudit` + 各单据时间线 | 增删改与状态迁移 |
| 单据审计 | lifecycle 迁移记录 + 各模块 history 页 | 提交、审批、过账、冲销 |
| 统一查询 | 无 | — |

## 2. 十问逐条

| # | 问题 | 现状 | 判定 |
| --- | --- | --- | --- |
| 1 | 权威来源是谁 | 账号、角色、权限集归 NocoBase 授权插件；岗位绑定归组织；复核配置归 lifecycle 参数库 | 合规 |
| 2 | 写权限到哪一级 | 改账号、角色要对应 settings 动作；改复核配置要对应单据的配置权限 | 合规 |
| 3 | 是否审核、几级 | 配置本身不审批；保存靠版本号防并发 | 合规（配置类） |
| 4 | 何时生效 | 保存即生效；已在途单据用快照，不受影响 | 合规 |
| 5 | 填错怎么改 | 直接改，生成新版本；没有回滚按钮 | 部分，见 C6 |
| 6 | 业务日期与录入日期 | 配置无业务日期；版本表带时间与操作人 | 合规 |
| 7 | 能否追到来源单据 | 单据里存 `parameterSnapshot`，能回看当时配置 | 合规 |
| 8 | 附件证据 | 两套表，未统一 | 缺口，见 C4 |
| 9 | 被谁引用、引用后能否改 | 所有走审批的单据；改配置不影响在途单 | 合规 |
| 10 | 统计口径写在哪 | 无 | 不适用 |

## 4. 责任与待定

**谁负责**

- 系统管理员：账号、角色、权限集、默认权限。
- 组织管理员：岗位与权限集绑定。
- 各模块管理员：本公司该类单据的复核人配置。
- 具体人名待定；建议每个公司指定一名“审批配置负责人”。

**待业务决定**

1. 要不要做金额档审批？C2。要做的话，先定采购的金额区间。
2. 候选人解析不到时，是拒绝提交（现状）还是回退到某个固定角色？C3。
3. 附件是否统一成一张表？C4 已由总纲 §11 定方向，缺的是排期。
4. 审计检索页先做还是等财务模块一起做？C5。

**已成立、不需要再讨论的**

- 配置按公司隔离、带版本、带操作人、单据内快照，这四条与总纲 §5、§6 一致，保留。
- 候选人必须是本公司的人，跨公司审批要走集团角色，不靠“把别家公司的人加进候选人”。

## 5. 与其他模块的关系

- **采购、领用、仓库、销售共用一套审批引擎和一套配置机制**，只是页面分开。前面几个模块核对里提到的“审批人配置随时可改、在途单不受影响”，落点就在这里。
- **复核人资格依赖人事与组织。** 人事 H8（绩效上级靠 `reportsToId`）、组织 O4（部门负责人没人用）在这个模块里表现为“候选人解析不到就提交不了”。
- **附件问题是全局的**，不只采购：销售、仓库、安环（现场照片）都会遇到；安环核对里如果发现“照片没地方放”，根因在 C4。
- **审计问题是全局的**：组织、人事、物料、供应商各自有历史页，但没有一个地方能按人查。

## 6. 给后续模块的提示

1. 任何新模块要接审批，先看 `execution-review-service.ts` 的注册方式，不要另造一套配置页。
2. 新模块要存附件，先确认能不能复用 `supplyChainFiles`，不要再开第三张表。
3. 新模块要留痕，写进 lifecycle 迁移记录即可，不要只写 `updatedAt`。
