# 开发经验与踩坑记录

更新：2026-10-17。以下来自组织、人事与物料模块的实际开发与验收。后续新增记录写清现象、原因、处理、验证，避免只记结论。

## 先识别版本和官方能力

- 原服务器 alpha.13-full 与当前官方 V3 应用模板 beta.68 的开发架构不同。不能把旧插件教程直接套进新应用。通过 package.json、注册插件和应用本地官方 Skills 确认实际能力。
- 应用业务写在 client、server、database；复用代码先在应用内共享。需要跨应用独立发行时再拆插件。
- 权限、登录、用户、通知、调度优先使用已注册官方插件。页面菜单权限不能替代 API 权限；API 必须在输入校验前检查权限，避免泄漏信息。
- 官方 Skills 在 .agents/skills，由同步命令生成。项目经验写 docs 和 .agents/rules，不修改同步文件。

## 环境与依赖

- 本次模板要求 Node 24、pnpm 11。系统 Node 22 不符合要求；不要把依赖报错误判为业务代码错误。
- 受限 HOME 会导致缓存和包管理器写入失败。使用任务专用临时 XDG/npm 缓存。当前临时工具链入口 /tmp/nocobase-erp-env.sh 不作为长期安装依赖；新机器应正式安装对应工具链。
- shadcn CLI 拉取远端 registry 本次出现连接被关闭。可用可联网客户端获取官方原始 registry JSON，再由官方 CLI 安装本地 JSON；必要时临时托管原始颜色 registry。保留来源，不手写替代官方基础组件，不关闭 TLS 校验。
- Playwright 全量 Chromium 已下载时，channel: chromium 可以使用它；不必等待另一份 headless shell。浏览器运行还需可写缓存、配置目录和合适的运行权限。

## 组织业务与并发

- 主体、组织单元、岗位属于组织架构；人员、任职、兼职、调岗属于职能平台的人事管理，人力资源独立负责集团人才与规划。组织负责人引用岗位，不引入员工字段。
- 板块、区域是经营归属维度；集团空值表示不适用，不能解释为拥有全部数据权限。
- 检查循环和归属时，要在事务内先更新组织互斥行取得数据库写锁，再读取与验证，防止两个并发请求同时通过检查。SQLite/PostgreSQL 都已验证基本服务行为。
- revision/version 阻止旧表单覆盖新数据；组织互斥锁保护跨记录约束，两个机制用途不同。组织规则不要抽成无约束的通用 CRUD。
- 组织修改与审计同事务提交。停用保留历史；不能使用物理删除绕过依赖校验。

## 页面与验收

- 共用模型驱动六类组织资料，但使用官方 Table、Select、Calendar、RouteDialog/RouteDrawer/RouteChildPage。
- 保存成功先把返回记录写入详情缓存，再刷新列表、选项、历史，避免返回后瞬间显示旧值。
- 列表搜索使用 useUrlSearch，支持中文输入法和 URL 刷新恢复。测试刷新前必须等待 300ms 防抖结果写入 URL。
- 分类小表单按钮放 RouteDialog.footer，通过 form 属性关联真实表单；不能放进滚动正文。状态确认使用 onSubmit，支持回车。
- 大表单提交时同时禁用返回入口和表单操作。404 后刷新来源列表并停用缓存记录的操作，不能继续编辑已失效数据。
- 窄表格长文字使用 LongTextPreview；宽详情使用 LongText。类型和状态用文字徽标，颜色只作辅助。
- 截图应等待实际表单或表格出现；加载页不能当暗色验收，已有数据的列表不能标为空状态。模拟异常必须明确说明模拟范围。

## 部署顺序

- 本次异步 SCP 尚未完成时开始解压，造成截断包和缺失 Dockerfile。修正流程必须等待每个前置操作完成，检查退出码和 SHA256，再解压、构建、启动；脚本使用 subprocess.run(check=True) 或 set -e。
- 同一发布禁止并发执行两次部署；构建通过不等于部署完成。必须检查容器健康、真实登录、授权 API、静态资源和持久化。
- 使用独立目录、Compose 项目、数据库、端口；保留原 NocoBase 与 PLC 服务。发布包不包含密码、配置和数据。
- 更新前做 PostgreSQL 备份，保留上版镜像；配置密钥与数据都必须保留。初始管理员环境变量只用于首次初始化，不能拿它重置已有账号。

## 维护方式

每次遇到重复性问题，先更新此文件对应章节；确认可复用的实现写入《可复用能力目录》。只将长期有效的要求写入开发规则入口，不把临时路径当产品功能。

## 独立复核补充：数据刷新与流程界面

- 人才卡的基本资料、关联评价/任职/培养分属不同查询。页面 Refresh 必须明确刷新全部数据块，并保持繁忙状态直到子查询完成；只刷外层记录无法证明雷达和关联记录已更新。浏览器回归直接断言人才查询重新发出。
- 写接口可返回简略记录；不能把它当完整详情一直覆盖缓存。流程提交后必须补取含 workflow/currentStaffing 的完整详情，才能保留办理历史和下一步操作。新增实际“更新培养进展 → 返回详情 → 下一步按钮及新历史仍存在”的浏览器回归。
- 工作流表单与普通业务表单一样，需要字段旁错误、首错焦点和失败保留。评分依据、批准数量、完成结果与任务责任人先就地校验，后端字段错误映射回来；不能只有顶部通用 Alert。
- 主查询成功不代表页面成功：关联选项请求失败也要明确提示，不能把权限/网络错误显示成“—”或内部 ID。页面与关联查询一起处理和重试。
- 总览必须按指标说明筛选状态：已确认评价、未完成培养、待审批规划分别计数；不能用总记录数替代待办。回归测试加入未确认评价不增加确认数、培养完成后退出待办数。
- 浏览器窄屏无整页横向溢出不等于图表未裁切，必须查看图内文字；按容器宽度调整雷达半径和标签换行，并保留完整维度文本表。
- 浮点评分显示统一格式化；工作流内部 edit 也要有两种语言的历史文案。动态翻译键需按实际生命周期转移清单核对，不能只依赖静态字符串扫描。

- Base UI Button 即使 render 为 Link，实际可访问角色仍可能是 button。写浏览器选择器前核对真实快照和共享组件，不能从 JSX 标签猜角色；人事测试统一设置动作超时 10 秒，避免一个错误定位占用两分钟。嵌套 Drawer＋Dialog 选当前末层，不对同名父层点击。

## 物料中心：缓存、字段和上下文（2026-10-17）

- 新建保存后长时间停在“保存中”：给新记录 setQueryData 后再 refetchAll，会对没有 queryFn 的缓存触发默认重试。只主动刷新活跃详情，再使列表、选项和历史失效；组件测试采用真实默认重试配置，验证创建立即返回。
- 业务唯一冲突与版本冲突不能共用恢复动作：新建重复编码/身份时允许修改重交；编辑旧版本时保留输入并显式重载；动作重载保留原因。不能为新建记录请求 undefined ID。
- 模板、SKU 属性的动态输入除了 schema 校验，还必须注册 focus ref、必填标识和具体错误路径；数组选项的错误映射到实际 textarea，提交后聚焦首个无效控件。
- 详情中的包装、别名、标签和名称选项有独立查询，手动刷新应覆盖全部已展示来源。选项按实际溢出换行，标题仅在测得截断时显示全文提示。
- 共用详情被任务打开时，声明任务下的子路由和固定 kind/id 上下文；编辑及状态动作继承该上下文，保留查询条件逐层返回。
- 浏览器 toast 也可使用 dialog 角色；表单验收定位 route-overlay-content。覆盖页保留底层 inert DOM，测试等待当前层关闭并按当前层定位，不删除保护机制。
- shadcn CLI 的元数据请求发生 TLS 中断时，使用官方 registry 快照通过 CLI 生成组件，保留既有主题；不手写 primitive 或改写依赖源码。

## 物料中心发布验证补充

### 局域网 HTTP 的模板与状态页面故障

现象：线上“新建属性模板”点击“添加属性”后显示“无法加载 group-erp 的路由 warehouse-material-templates-new”，已有属性模板的编辑页及物料状态操作也可能失败。真实浏览器控制台为 `crypto.randomUUID is not a function`。页面统一错误边界同时承接渲染异常，不能仅凭“无法加载路由”认定是路由声明或静态文件丢失。

根因：生产以局域网 HTTP 提供服务，属于非安全上下文；`randomUUID` 不可用，而本机 localhost 测试仍属于可信上下文，未覆盖这个差异。改用应用已有的 `getRandomValues` 模式，抽出 `client/lib/random-id.ts`，保留状态请求重试键稳定和模板行键唯一。没有使用 `Math.random` 降低随机质量，也没有要求业务改入口地址才能使用。

回归覆盖：组件测试移除 `randomUUID`，验证模板新增/删除属性、已有模板编辑、状态动作打开及失败后同键重试；浏览器验证模板创建/编辑和 SKU 提交，并在真实生产 HTTP 地址复核。每次是否已部署及验证结果以发布记录为准。

- PostgreSQL 生产备份恢复到独立容器与 internal 网络，先验证新迁移、并发身份、版本、幂等和越权回滚，再切换正式应用。本次最终停机备份也恢复到了第二个隔离库，并核对原业务表数量。
- 当前 Docker 的 internal 网络不提供该容器的宿主机发布端口。保持禁止外连，通过前台 SSH 隧道直达核对过的容器 IP；隧道设置独立 ControlPath，结束时用控制命令退出。工具的进程隔离下，结束父 shell 不一定清理 SSH 子进程；不要依赖后台 fork 后的存活状态。
- 页面加载会正常 PUT i18n/locale。只读业务验收若无差别 abort 所有非 GET，会人为制造网络控制台错误；阻断业务写入，但允许该固定语言偏好请求，并在结果说明。区分探针导致的异常与产品故障。
- 本次正式发布及重启验证见 [仓库物料中心发布记录](仓库物料中心发布记录.md)。历史发布记录保留，当前版本与备份在根交接文档同步更新。

## A2.1 选料与共同事务验证

供应商适用范围接续：权限服务创建的 Permission Set 在 Repository 读取 grants 时可能为 JSON 文本，安装种子也可能提供 JSON 值；增量补依赖需正确解码并保留原存储形态，不能遍历字符串字符后误认为已升级。公共服务生成的 permission-set ID 也不保证等于 key，更新必须使用实际 ID 或唯一 key。新增覆盖了真实服务创建配置、重复升级及保留公司范围的测试。

范围继承不能把“没有公司覆盖”与“覆盖记录被当前读策略隐藏”混为一谈。后者必须收紧可用性，不能让单公司停用变成默认启用；配置区域/公司明细只可见部分时也应拒绝整组修订，避免把不完整快照当成完整配置。相应回归在 `tests/logic/partner-applicability.test.ts`。

供应商 A2.2 本地接续补充：官方 defineDatabasePermission builder 的 create/update 返回新 builder，必须继续使用返回值；只调用而丢弃返回值会使资源只含 read，管理员和普通授权账号均在生命周期写入前得到 403。seed 的 upsertOne 不接受空 update，应使用不改变业务含义的非空更新或先 exists 后 create。已以真实应用启动、普通账号 CRUD、独立写字段/写范围及重复 seed 验证，详见 `tests/logic/suppliers.test.ts`。

- 通过 SSH `bash -s` 发送部署脚本时，`docker compose run -T` 仍可能读取标准输入，吞掉后续脚本并以 0 退出。运行非交互 CLI 时明确加 `< /dev/null`，检查后续阶段的结果文件和目标镜像；不能仅凭 SSH 退出码判断整份脚本执行完毕。

## 移除物料分类：迁移及权限接续（2026-10-17）

- SQLite 在删除被 SKU 引用的名称表字段/外键时，Knex 会临时重建表。在事务内不能关闭 foreign_keys；新增迁移按 [SQLite 官方延迟外键说明](https://www.sqlite.org/pragma.html#pragma_defer_foreign_keys) 将检查延迟到事务末，完成后先执行 foreign_key_check 确认完整性再恢复即时检查。索引先独立删除，避免删列时索引已被移除导致重复 drop。迁移测试保留真实 SKU 引用，不能只测空表。
- 迁移任务 connection.client() 是异步且类型为 unknown，先 await，再收窄所需 raw 能力；业务回填使用同一任务 query，JSON 审计快照用 Repository 正确编码。新迁移/seed 被 Prettier 历史保护忽略，首次格式化仅对这两个新文件显式使用空 ignore-path，不格式化旧历史。
- 权限初始化可能留下 JSON 字符串或数组形式的 grants。增量配置先解析，再只删旧分类 grants/scopes，更新时保留原表示、其它权限和成员分配；对平台拥有的非列表 grants 不改动。SKU 新增标签筛选的依赖只授予只读范围。测试包含定制角色、显式空范围、重复执行和公司选料边界。
- 旧 URL 的 categoryId/parentId 不能因请求白名单变化而被静默忽略。页面先显示失效筛选且不请求列表，用户清除后再查询并聚焦搜索；服务端严格拒绝旧字段/参数。标签筛选同时覆盖名称继承和 SKU 直接关联，列表计数及详情标签去重。

- 旧筛选异常态不能只设置 useQuery enabled=false；手动 refetch 仍可绕过。隐藏刷新/计数/分页并在 queryFn 守卫，独立验收覆盖维护/只读 × categoryId/parentId 四条路径及 reload、清除聚焦。截图等待有限动画完成，列表等待最终行和选中标签，避免将加载或过渡帧当成最终效果。长路径拼接旧备注时遵守新标签原有 6000 字校验上限，完整原值留审计，避免迁移后无法编辑。

## 采购申请后端首批：官方契约验证（2026-10-18）

- **CHECK 声明不等于物理约束**：beta.20 的能力规划器明确跳过 CHECK 编译；实际插入零数量证实未生效。采购新迁移仅对该缺口使用事务 driver 的 PostgreSQL CHECK／SQLite 约束触发器，物理标识从官方 Query 编译结果提取，严格检查引用和无绑定值。SQLite 和后续 PostgreSQL 专项均已实际验证直接非法写入、组合外键及 up/down/up，见 [采购专项记录](采购A2.2隔离PostgreSQL验证.md)。
- **审核选择器的未配置默认值**：官方 normalizeReviewerSelections 要求 1—100 条且 group 为正整数。应用仅为“未配置、可存草稿”接受空默认值；配置保存拒绝空值，正式提交拒绝无候选，不虚构默认账号。配置与任务用官方存储及选择器，不另写审批系统。
- **条件性授权仍需消费其 policy**：公司限定的 delegate 决策可能是 conditional。拒绝 deny 后消费返回的数据库策略，按目标主体再次判断；既不能误拒绝所有限定公司许可，也不能转成不分公司的布尔权限。
- **类型化筛选器匹配字段类型**：text 用 f.text，业务日期建为 date 并用官方 notBefore/notAfter；f.string 不能用于 text 或日期运算。实际搜索与日期范围 API 测试覆盖，不以静态类型通过替代运行验证。
- **隔离套件中的配置编辑**：官方应用测试在文件内复用隔离应用；测试断言按自身主体/父单限定，失败注入比较基线，不能假设每项之前数据库为空。改权限模板标题须用 encodeAuthorizationTitle；直接写裸字符串会让后续真实授权读取失败。

## 2026-10-22 整改：防止模块各自为政

- 现象不是“页面没写完”，而是同一件事被复制了多次：16 个页面各自读 `subjectId`、各自放公司选择器、各自决定未选时的文案；4 个审核菜单后面是 3 份 500 行左右的编辑器。只修其中一页，下一次新增模块还会照抄旧页。整改必须同时处理“共享机制”和“防止再抄”的检查。
- 公司作用域保留 URL 参数，不改成全局 store：深链、刷新、后退都依赖 URL。壳层只做两件事——记住最后一次选择、在缺参数时补回；页面统一用 `CompanyScope`/`CompanyPicker`，单公司自动选中和失效记忆清理也在共享组件里。不要做“全局默认公司”，没有公司档案时会把空态变成 403。
- 审核规则必须只有一个事实源：`@nocobase/lifecycle` 的 `parameterConfiguration`。服务端 `reviewRuleFields()` 通过 `runtime.describe()` 取字段，只返回可序列化的 `{key,type,title}`；客户端不复制字段常量。`requireProject` 这类锁定为 false 的字段要显式排除，否则会被渲染成可编辑开关，保存时才报错。
- 参数表没有合并：采购一套、领用/执行共用一套；scope 键分别以 `procurement:`、`requisitions:`、`${kind}:` 开头。合并要搬历史行并重建 revision/幂等语义，收益只是“少一张表”，不值得在整改里做。统一的是构造 scope 的函数（`reviewScope`）和字段描述，不是存储。
- NocoBase 3 的 `findMany({ filter: {} })` 会被判为非法空条件，报 `Filter shorthand must not be empty`；迁移里要省略参数直接 `findMany()`。这个错误会让所有数据库测试在迁移阶段失败，先看第一个迁移错误，不要逐个修业务断言。
- 锁定字段/空条件/ABI 这类问题，单测和类型检查都发现不了，必须跑真实迁移和全量测试。Node 24 构建后原生模块指向 ABI 137，切回 Node 22 会加载失败；版本文件、README 和交接文档要同时写清楚。
- 防回归用 `tests/logic/architecture-guard.test.ts` 扫源码：条件表是否被复制、公司门禁文案是否回到页面、403 是否回到裸 `<p>`、审核菜单是否重复、字段描述是否仍由服务端生成。例外要窄（例如组织错误组件内的 `<p>` 不是整页门禁），不能用整目录白名单把检查架空。

## 2026-10-23 测试数据暴露的两个坑

- **空过滤不是“无过滤”**：NocoBase 3 的 repository 把 `filter: {}` 当成非法简写，报 `Filter shorthand must not be empty`。列表在没有任何筛选条件时不要传 `filter`，或补一个真实条件；资产列表、迁移 `findMany({ filter: {} })` 都踩过。
- **岗位成员不在员工表**：`personnelEmployees.positionId` 是空列；在岗关系在 `personnelAssignments`（`personId` + `positionId` + `status`），员工 `id` 就是 assignment 的 `personId`。岗位人数、岗位授权同步必须从 assignment 出发，不能从员工表字段出发。
