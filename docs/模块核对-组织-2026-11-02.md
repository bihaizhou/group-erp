# 模块核对 · 组织（第五位）

v0.1 · 2026-11-02 · 依据《数据来源分类与治理约定》v1.7（下称“总纲”）
核对范围：`client/pages/organization/`；`server/providers/organization-model.ts`、`organization-service.ts`；`server/routes/organization.ts`、`position-permissions.ts`；迁移 `202610160001_organization.ts`、`202611010008_position_permission_sets.ts`
核对表：`orgSubjects`、`orgUnits`、`orgPositions`、`orgSectors`、`orgRegions`、`orgRelations`、`orgAudit`、`orgMutationLock`

## 0. 结论

- **组织是六张表，不是一棵树。** 主体（集团 / 公司 / 共享服务）、部门、岗位、板块、区域、组织关系，各自独立建、独立改，靠 `parentId`、`subjectId`、`unitId`、`reportsToId` 连起来。
- **只停用，不删除。** 没有删除接口，只有启用 / 停用；停用前会挡：还有下级、还有在用岗位、还被采购 / 领用 / 仓库 / 人事引用。这是目前几个模块里校验做得最厚的一处。
- **改了就生效，没有审批、没有生效日。** 保存即生效，只留一条审计（改前 / 改后 / 谁 / 为什么）。没有“下月一号起调整”的能力。
- **权限只有一个开关。** 读写都挂在 `settings/organization` 上：能改的人可以改任何一家公司，没有按公司分权。
- **两张表录了没人用。** 组织关系（`orgRelations`）只有本模块自己读写，没有任何业务模块消费；部门负责人（`leaderPositionId`）只在页面上显示，没进审批人解析、也没进任何流程。
- **改名不回填。** 业务单据只存公司 `subjectId`，名称是实时关联取出来的。公司改名后，历史单据、历史打印件显示的都是新名字。

## 1. 来源清单

### 1.1 六类主数据

| 对象 | 表 | 关键字段 | 谁维护 | 约束 |
| --- | --- | --- | --- | --- |
| 主体 | `orgSubjects` | `type`（group / company / sharedService）、`parentId`、`sectorId`、`regionId`、`registrationCountry`、`registrationNumber`、`shortName` | 组织管理员 | 公司必须同时有板块和区域（`ORG_COMPANY_CLASSIFICATION`）；`parentId` 不能成环 |
| 部门 | `orgUnits` | `type`（department / center / division / projectDepartment / other）、`subjectId`、`parentId`、`leaderPositionId`、`duties` | 组织管理员 | 上级部门必须同公司（`ORG_UNIT_SUBJECT_MISMATCH`）；负责人必须在本部门（`ORG_LEADER_UNIT_MISMATCH`）；有下级 / 岗位 / 关系时不能换公司（`ORG_UNIT_SUBJECT_LOCKED`） |
| 岗位 | `orgPositions` | `unitId`、`reportsToId`、`duties`、`requirements`、`productionRole` | 组织管理员 | 上级岗位必须同公司（`ORG_POSITION_SUBJECT_MISMATCH`）；`reportsToId` 不能成环；本人是部门负责人或有下级时不能换部门（`ORG_POSITION_UNIT_LOCKED`） |
| 板块 | `orgSectors` | `parentId` | 组织管理员 | 公司分类用；被公司引用时不能停用 |
| 区域 | `orgRegions` | `parentId` | 组织管理员 | 同上；供应商、采购、库存也用 |
| 组织关系 | `orgRelations` | `type`（management / service / collaboration）、`sourceKind/sourceId`、`targetKind/targetId`、`startDate`、`endDate` | 组织管理员 | 不能自己连自己；结束日不能早于开始日；源和目标只能是主体或部门 |

公共字段：`code`（大写，`^[A-Z0-9][A-Z0-9_.-]{0,63}$`，全局唯一）、`name`（1–200）、`sortOrder`、`status`（active / inactive）、`revision`。

### 1.2 写入与留痕

| 动作 | 入口 | 校验 | 留痕 |
| --- | --- | --- | --- |
| 新建 | `POST /organization/:kind` | 编码唯一、引用存在且启用、跨公司一致性、成环 | `orgAudit`：create，存改后全量 |
| 修改 | `PATCH /organization/:kind/:id` | 同上 + 乐观锁 `version`（`ORG_VERSION_CONFLICT`）、必填 `reason` | `orgAudit`：update，存改前 + 改后 |
| 启用 / 停用 | `POST /organization/:kind/:id/setStatus` | 停用前置：下级、在用岗位、采购 / 领用 / 仓库 / 物料 / 人事引用 | `orgAudit`：enable / disable，必填 `reason` |
| 并发 | 所有写操作先锁 `orgMutationLock` 一行 | 串行化拓扑检查，防止两边同时挪动 | 不单独留痕 |

停用前置校验分四组，错误码不同：
- `ORG_ACTIVE_DEPENDENTS`：还有启用的下级、岗位、负责人引用、启用中的组织关系。
- `ORG_PURCHASE_DEPENDENTS`：还有未结束的采购申请（按公司 / 部门）。
- `ORG_ISSUE_DEPENDENTS`：还有未结束的领用申请。
- `ORG_MATERIAL_DEPENDENTS`：还有启用的仓库、物料公司设置、物料主数据、未结束的物料申请；岗位还关联仓库负责人。
- `ORG_PERSONNEL_DEPENDENTS`：还有未结束的任职、劳动关系、在途异动（草稿 / 待审 / 已批未生效）。

### 1.3 岗位与权限

岗位 → 权限集的绑定在 `position-permissions` 页面维护（`PUT /position-permissions/:id`，传 `permissionSetKeys`；落表 `positionPermissionSets`）。这就是“账号 → 任职 → 岗位 → 权限集 → 数据范围”那条链里“岗位 → 权限集”的一环。绑定变更不影响已登录会话的当前权限，按权限集刷新规则生效。

### 1.4 派生

| 派生 | 算法 | 落表 |
| --- | --- | --- |
| 组织总览 | 六类各自的启用数、停用数 | 无（实时统计） |
| 编制 / 在岗 | 人事模块按岗位汇总，不在组织里算 | 无 |
| 变更历史 | 读 `orgAudit`，按时间倒序 | 无 |

## 4. 责任与待定

**谁负责**

- 业务责任人：组织管理员（集团层面）、各公司负责人（本公司结构确认）。具体人名待定。
- 系统责任人：组织模块迁移、`position-permissions` 绑定、本文档同步。改组织字段或加类目必须回来改本文第 1 节。

**待业务决定**

1. 组织调整要不要审批和生效日？O1。若只做“生效日”不做审批，成本低一半。
2. 组织是集团统管，还是按公司分权？O2。这条决定权限怎么配，不改代码也能先落制度。
3. `orgRelations` 留不留？留的话谁用、用在哪；不留就在页面标“暂未使用”。
4. 部门负责人要不要接进审批解析？O4。
5. 公司改名后，历史单据显示新名还是当时的名？O7。

**已成立、不需要再讨论的**

- 只停用不删除、停用前查引用，与总纲 §7“不覆盖历史”一致。
- 编码唯一、跨公司一致性校验、成环检测、并发串行化，这四项做得比其余模块都严，保留。

## 5. 与前面模块的关系

- **人事依赖最深。** 岗位 `reportsToId` 决定绩效“上级评价”；岗位停用会让审批人解析落空；员工归属公司、任职、编制都挂组织。人事核对里的 H8 就是这条。
- **采购、领用、仓库靠它判“公司内”。** 采购申请校验公司 / 部门 / 员工归属，仓库校验仓库与物料公司设置，都直接读组织表。
- **组织是唯一“改了就生效”的主数据。** 采购、仓库、生产、人事的单据都有状态机，组织没有。这不是错，但和组织调整的严肃性不匹配。
- **组织停用不检查资产。** `organization-service.ts` 里没有资产引用检查；部门停用后，挂在它名下的资产不会报警。资产核对时要补这条。
- **权限链在这里闭环。** 前面几个模块反复出现“岗位决定权限、不决定公司”，落点就是 `position-permissions` 这张绑定表。

## 6. 给下一位（资产）的提示

1. 资产一定会挂部门和使用人，组织这边没有“资产归属”字段，核对时先看资产表自己存了什么。
2. 组织停用会挡人事、采购、领用、仓库，但不会挡资产；资产核对时确认“部门停用后资产怎么算”。
3. 如果资产要做“移交”，参照人事异动的做法：留 `snapshot`，不要直接改归属。
