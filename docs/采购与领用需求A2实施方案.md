# 采购与领用需求 A2 实施方案

方案日期：2026年10月17日；状态更新：2026-10-18。A2.1选料、A2.2供应商/范围与停用、采购申请/审核配置和跨模块引用协调已发布并重启验收，见 [采购发布记录](采购A2.2发布记录.md)。既有实施记录保留各阶段验证，领用、正式治理来源与结果回写及私有需求附件仍待续，A2整体未完成。工程为现有 `group-erp`。用户已确认：**需求审批与物料治理允许并行进行**。

A2 交付采购申请、领用申请及其与物料治理的逐行关联。申请人可以直接选择已启用物料，也可以先描述未知物料；治理结果返回原明细，由申请方确认后用于后续业务。审批、物料识别分别显示，原始需求和已审批内容均可追溯。

本期包括采购模块的供应商及公司使用关系、领用模块的用途与规则、私有需求附件。采购订单、实际收货、领用发放与退回、库存余额和数量流水按 B 阶段建设。A2 页面不能出现“已入库”“已发放”的人工填写入口。

总体边界见 [采购销售仓库与物料治理架构方案](采购销售仓库与物料治理架构方案.md)，现有能力见 [A1 实施与现状](仓库物料中心首期实施方案.md) 和 [当前发布记录](物料中心分类移除发布记录.md)。A2.1 已随 `materials-tags-20261018-043000` 发布到搭建环境；A2.2供应商及采购后续已发布，领用和治理回写仍不能算作已交付。

## 基础资料与审核配置

### 供应商及公司使用关系

用户后续已明确按区域、指定项目公司或全部项目公司适用，并区分全局与单公司停用；当前规则及已实现接口以 [供应商客户适用范围与停用规则](供应商客户适用范围与停用规则.md) 为准。本节较早的“公司关系”描述继续用于单公司覆盖，不能据此遗漏区域或全部继承。

供应商使用 `businessPartners` 保存公共身份，以 `partnerSubjectSettings` 保存各公司的供应商使用关系。A2 只开放采购入口和供应商角色；未来销售模块经过明确授权后复用同一身份，不提前建设客户管理页面。

| 对象         | 字段                                                                         | 规则                                                                          |
| ------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 往来身份     | `id`、`code`、`name`、`registrationCode`、`status`、`revision`、创建更新时间 | 稳定 ID；编码唯一；统一登记标识可空，有值时规范化并防重复；名称相似只提示查重 |
| 公司使用关系 | `id`、`partnerId`、`subjectId`、`partnerRole`、`status`、`revision`、`notes` | A2 的角色固定为 `supplier`；同主体、往来身份和角色唯一                        |
| 资料维护     | 原因、经办账号、前后值                                                       | 停用留历史；公司人员只能维护自己的使用关系，公共身份维护另授权限              |

采购申请不强制指定供应商，也不要求在申请时决定实际采购主体之外的交易安排。本期不建供应商价格、银行账户、合同及专用货号。普通申请人的供应商选项只返回本公司已启用关系和最小识别字段。

新建身份和首个公司使用关系在一个事务提交。若查重命中无权读取的既有身份，返回不泄漏资料的冲突提示，由获授权的主档维护人员核对关联；不以公开全集团供应商列表解决查重问题。停用使用关系后不能新增引用，历史申请继续显示提交时快照。

### 领用用途

`materialIssuePurposes` 保存 `id`、公司 `subjectId`、`code`、`name`、适用说明、`status`、`revision` 和审计字段。同公司用途编码唯一，领用提交时必须选择本公司启用用途。初始化不写入虚构的正式用途，业务人员可按实际需要维护。

用途只说明业务目的，不能决定物料身份或直接生成出库。生产任务领料在 B 的独立来源规则建设，不能通过增加一个“生产”用途绕过生产凭证校验。

### 官方生命周期参数

本地已安装 `@nocobase/lifecycle` `0.1.0-beta.2`，其公开声明导出 `StoredLifecycleParameters`、`normalizeReviewerSelections` 和 `resolveReviewerSelections`。本期采用该能力保存代码声明的固定参数，继续使用同一个 `recordLifecycleToken`，不建设第二套审批引擎或流程编辑器。

按“业务模块 + 主体”确定参数 scope，由服务端从单据归属解析。配置组包括采购审核规则和领用规则；`materialIssueRules` 在本期是领用参数组的业务名称，不再增加一张重复存储同一配置的规则表。

| 参数                      | 默认与校验                                                        | 生效方式                                             |
| ------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------- |
| `reviewerSelections`      | 显式选择本主体可用的岗位或账号；无候选时拒绝提交，不自动使用 root | 首次正式提交冻结规则；每轮审核任务再解析当前有效人员 |
| `allowParallelGovernance` | 默认为 `true`；业务已确认允许并行                                 | 首次提交冻结；为 `false` 时需先确认所有物料          |
| `requireProject`          | 项目档案未接入时固定为 `false`，拒绝配置成 `true`                 | 预留后续受控接入                                     |
| 领用管理方式              | 代码固定为仅库存类物料                                            | 申请人不能自行放宽                                   |

岗位使用代码声明的 `position` selector，按集团业务日期解析有效主职及允许的兼职；账号 selector 同样过滤停用账号、无当前资格者及自审人员。规则快照冻结的是选择条件；每轮任务生成后，其实际候选账号保持固定。一阶段审核中任一候选人可以决定，以版本条件保证并发只成功一个决定。

首次成功提交保留官方参数快照。退回、撤回、修改后重提沿用该记录的原规则；下一轮审核任务重新生成候选账号。需要改用新规则时，显式取消原申请并复制为关联的新申请，保留两者联系，不覆盖旧规则快照。候选全部失效时，通过有独立授权的“重新指定审核人”动作保留原因和前后候选，不能后台悄悄改人。

配置页明确显示适用公司、审核岗位、并行选项、当前版本和生效时点。完整参数组采用版本条件保存，冲突保留用户输入。具体岗位及账号由业务配置；没有配置时可保存草稿，提交会解释缺少哪项职责。

## 单据与明细字段

### 两类单头

采购和领用分别使用 `purchaseRequests`、`materialIssueRequests`，不把两类单据和物料治理任务合并成万能单据表。

| 字段                                            | 采购申请       | 领用申请       | 保存与提交规则                                             |
| ----------------------------------------------- | -------------- | -------------- | ---------------------------------------------------------- |
| `id`、`code`                                    | 必有           | 必有           | 系统生成稳定 ID 和唯一单号；单号不随修改重建               |
| `subjectId`                                     | 业务承担主体   | 领用承担主体   | 草稿即必填，校验启用与本次动作范围；首次提交后不能更换主体 |
| `requesterEmployeeId`                           | 实际申请人     | 实际申请人     | 提交必填；与经办账号分开保存                               |
| `recipientEmployeeId`                           | 不使用         | 实际领用人     | 领用提交必填；必须有本主体有效用工及适用任职               |
| `requestingUnitId`                              | 申请部门       | 申请部门       | 提交必填；引用本主体启用组织单元                           |
| `purposeId`                                     | 不使用         | 本公司用途     | 领用提交必填；不能使用其他公司用途                         |
| `usage`、`neededOn`                             | 用途和需求日期 | 用途和需求日期 | 提交必填；日期使用集团业务日期，不用浏览器时区推算         |
| `suggestedSupplierId`                           | 可选供应商身份 | 不使用         | 采购有值时须有本主体有效供应商关系，审批不构成订单承诺     |
| `projectId`                                     | 当前为空       | 当前为空       | 正式项目服务接入前拒绝非空值，不创建临时项目选项           |
| `notes`                                         | 可空           | 可空           | 长度限制和双语错误提示                                     |
| `status`、`statusChangedAt`、`lifecycleVersion` | 生命周期字段   | 生命周期字段   | 只能由共享官方运行时创建和推进                             |
| `revision`、`contentVersion`、`governanceEpoch` | 版本字段       | 版本字段       | 分别用于记录并发、审批内容和治理来源有效期                 |
| `submittedVersionId`、`approvedVersionId`       | 快照引用       | 快照引用       | 服务端填写；只有当前批准内容才具备后续执行资格             |
| `createdBy`、`updatedBy`、提交及批准时间        | 经办账号与时间 | 经办账号与时间 | 从登录身份和服务端时钟生成，客户端不能冒填                 |

草稿可以保存尚未齐全的业务内容，但所有已填写引用都必须合法且在权限范围内。首次创建至少确定主体并保存真实经办身份；正式提交要求完整单头及至少一条有效明细。部门与实际人员关系按提交日有效任职检查，集团代办也不能把其他公司人员随意塞入本公司单据。

### 两类逐行明细

`purchaseRequestLines`、`materialIssueRequestLines` 保存明确字段，父单 ID、行 ID、数量、单位和识别结果不放入不可约束的整单 JSON。每行分配稳定 `id`；排序、插入和删除其他行不改变它。

| 字段                                                                     | 含义与约束                                                        |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `id`、`requestId`、`subjectId`、`lineNo`                                 | 父单与主体一致；行号在单内唯一；不接受跨单拼接行 ID               |
| `status`、`revision`、`inputRevision`                                    | 行启用或取消、记录版本、需求输入版本；已提交行取消须留原因和历史  |
| `governanceAttempt`                                                      | 本行治理轮次；显式重新提报时在版本条件下增加，普通重试不增加      |
| `originalName`、`originalSpecification`                                  | 保存当时原始叫法和规格；后续治理不覆盖原文，修改形成新输入版本    |
| `materialNameId`                                                         | 可先选统一名称；仅选中名称不等于已识别具体物料                    |
| `requestedQuantity`、`requestedUnitText`、`requestedUnitId`              | 原始需求数量和单位；未知单位允许保留文字，有字典 ID 时校验启用    |
| `skuId`、`managementModeSnapshot`                                        | 申请方已经确认的具体物料及管理方式；未知时为空，不能填治理任务 ID |
| `unitId`、`unitRuleId`、`unitRuleRevision`                               | 已确认业务单位、具体包装规则及其版本；同为“箱”也必须明确包装      |
| `numeratorSnapshot`、`denominatorSnapshot`、`baseUnitId`、`baseQuantity` | 固定换算和需求基准数量快照；这是需求量，不是库存发生量            |
| `identificationStatus`、`activeSourceLinkId`                             | 逐行识别进度和有效治理关联，由受控服务填写                        |
| `materialSnapshot`、`confirmedBy`、`confirmedAt`                         | 确认时名称、规格、单位展示信息与确认账号；后续更名不改写提交快照  |
| `usage`、`notes`                                                         | 本行用途补充；不以备注承载正式主体、项目或数量字段                |

数量沿用 A1 的明确十进制输入边界，最多 18 位整数、6 位小数，以字符串传输，使用十进制定点整数或精确分数计算。数量必须大于零并满足所选单位精度；换算结果超过存储范围、产生不允许的小数或不能精确表示时拒绝，不能静默四舍五入。以基准单位申请时固定比例为 `1/1`。

未知物料可以暂存“20 副”或“3 箱”，但不能猜测一副含几个、一箱含多少。治理返回 SKU 后仍要确认业务单位和包装，确认前不能形成可执行基准数量。砂石吨与立方米之间没有确定比例时保持待补充，A2 不构造重量体积换算。

建议初始单据上限为 100 行、列表每页最多 100 条，服务端执行相同限制。关联选择采用搜索与分页，不复制人事现有一次读取 1000 条的容量边界作为新业务方案。

### 内容快照与审核任务

`supplyChainRequestVersions` 按单据种类、单据 ID 和 `contentVersion` 保存不可覆盖的提交内容，包含单头、有效明细、组织人员名称、已确认物料及单位、附件关联和参数快照引用。批准明确指向本轮提交快照，不读取当前可变明细来解释历史批准。

`supplyChainReviewTasks` 保存单据种类与 ID、审核轮次、提交快照 ID、候选账号、实际决定人、决定及原因。每单每轮只有一个有效审核任务。候选列表是该阶段的事实，不作为通用多人会签平台。所有审核决定仍通过对应申请的官方生命周期推进；任务只保存本轮办理资格和结果。

草稿内容变更推进 `contentVersion`；返回候选只推进记录版本。撤回、退回、修订或接受新物料导致旧提交失效时，清空当前提交及批准的有效引用，旧快照和审核任务仍在历史中。相同内容重新提交可复用内容快照，但要创建新的审核轮次，不能复活旧审核任务。

## 申请生命周期与物料识别

### 申请状态和操作

两类申请采用相同的固定阶段，分别注册生命周期定义。`approved` 不是不可退出的最终态，以便通过受控修订撤销当前执行资格；`cancelled` 是终态。

| 操作             | 状态变化                                 | 约束和结果                                                                           |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------------------------------ |
| 创建、保存       | 新建为 `draft`；编辑为草稿自迁移         | 保存版本条件、已填引用及审计；编辑不直接写状态                                       |
| `submit`         | `draft → pending`                        | 完整校验，冻结内容与参数依据，生成本轮审核任务；未知有效行原子创建或复用有效治理关联 |
| `approve`        | `pending → approved`                     | 当前候选人及动作范围均有效、防自审；批准当前快照，允许识别尚未完成                   |
| `return`         | `pending → draft`                        | 审核人填写原因；本轮任务结束，旧治理关联失效，保留历史与原始输入                     |
| `withdraw`       | `pending → draft`                        | 申请方或授权代办撤回；增加来源有效期版本，关闭本轮任务和旧治理关联                   |
| `revise`         | `approved → draft`                       | 明确填写原因，撤销当前审批的可执行资格，保留旧批准快照；修改后重新提交               |
| `acceptMaterial` | 草稿保持草稿；`pending/approved → draft` | 确认治理候选、单位和换算；改变已提交内容时结束旧审核轮次，更新内容版本，重新提交     |
| `offerMaterial`  | 当前状态的系统自迁移                     | 仅登记有效来源行的候选及识别进度，不改变已审批的 SKU、数量、单位或内容快照           |
| `cancel`         | `draft/pending/approved → cancelled`     | 原因必填；关闭任务和来源关联；B 接入履约后另加未执行依赖检查                         |

`offerMaterial` 等内部动作设置为 `manual: false`，普通请求不能随意调用。候选返回也会推进记录的 `revision` 和生命周期版本，审批页必须刷新详情；它不改变 `contentVersion`，当前审核人仍可对已经冻结的需求作决定。

并行流程可以表现为“审批已通过，2 行物料待确认”。这不代表可以下采购订单或领用出库。后续 B 的执行准入必须同时满足：当前状态批准、批准快照与当前内容一致、全部执行行完成识别、实时公司准入及引用仍有效。

若在待审批时接受任一新物料结果，申请回到草稿，原审核任务立即失效；待其他行确认完毕后一次重新提交即可。接受结果本身不使其他未改动行的治理任务失效。用户主动撤回、退回、取消或另行修订，则按来源版本规则关闭旧关联。

### 逐行物料识别状态

| 状态                   | 页面含义                   | 可进行的下一步                                   |
| ---------------------- | -------------------------- | ------------------------------------------------ |
| `unidentified`         | 仅有原始需求或统一名称     | 选择具体物料，或提报治理                         |
| `governing`            | 已关联有效治理任务         | 查看进度；按授权补充原始需求                     |
| `needsInformation`     | 治理要求补充规格或单位     | 修改该行并重新提报，保留旧关联历史               |
| `awaitingConfirmation` | 治理结果已返回             | 核对 SKU、管理方式、单位包装后接受，或说明不匹配 |
| `identified`           | 具体物料和数量单位已经确认 | 提交、审批；后续执行仍重新检查实时可用性         |

行取消由行的 `status` 表达，不与识别状态混为一谈。已知物料在保存时校验通过即可进入 `identified`；未知行不能由客户端直接声明该状态。整单识别进度由有效行统计，展示总行数、待治理、待确认和已识别数量。

```mermaid
flowchart LR
  A[保存需求与原始明细] --> B[提交需求]
  B --> C[负责人审核用途与数量]
  B --> D[未知行交物料管理员整理]
  D --> E[查重或建档并独立审核]
  E --> F[结果返回原行等待确认]
  F --> G[申请方确认物料与单位]
  C --> H[保留本轮审批结果]
  G --> I[内容变化后重新提交审核]
  H --> I
  I --> J[当前内容批准且全部物料确认]
```

图中结果到达与审核决定没有固定先后顺序。原本全部选择已知物料的申请，可以直接批准，无需经过治理支路。

## 公共选料契约

### 已有接口和需要补齐的行为

本次使用原管理员会话只读取了生产 OpenAPI，核对到以下现有接口；没有创建 API Key 或提交业务单据。

| 已有接口                                    | 当前可直接复用                     | A2 必须补齐                                            |
| ------------------------------------------- | ---------------------------------- | ------------------------------------------------------ |
| `GET /api/materials/catalog`                | 启用 SKU、名称、属性及全局别名检索 | 本主体业务准入、公司别名解析、明确的业务上下文         |
| `GET /api/materials/catalog/{id}`           | 公共物料详情与启用包装             | 选定公司和业务类型下的实时可选原因、规则版本快照       |
| `POST /api/materials/requests/{id}/resolve` | 治理任务办结及任务与 SKU 关联      | 来源行校验、同事务候选回写；现有契约不承诺来源回写     |
| `GET /api/people/options`                   | 已有人事范围的选项                 | 不直接授予申请人此接口权限；新增本业务最小人员选择接口 |

现有目录接受查询参数不等于实际执行公司采购开关。A1 公共目录只使用已启用的全局映射，不能传一个 `subjectId` 就宣称公司别名和准入已生效。

A2 新增业务选料门面，底层提取并复用 `MaterialService` 的目录查询与详情组装。在业务上下文中应用公司范围、别名和准入，不从维护接口读取草稿。公共目录保留现有语义和页面行为。

### 公司范围和默认拒绝规则

选料门面显式接收业务主体和业务类型，服务端验证本次动作对该主体的权限；已保存申请的上下文从父单读取。前端切换主体时清空尚未确认的物料选择，并要求重新查询，不继续使用前一公司的别名和准入结果。

| 情况                               | 采购                           | 领用                                       |
| ---------------------------------- | ------------------------------ | ------------------------------------------ |
| SKU、名称或单位失效                | 不可新选，不可提交或确认       | 同左                                       |
| 没有本主体公司物料设置             | 不可业务选用；提示需要维护准入 | 不可业务选用；提示需要维护公司使用关系     |
| 设置 `inactive`                    | 拒绝                           | 拒绝                                       |
| 设置 `active`、`canPurchase=false` | 拒绝                           | 不以此开关判断；仍检查领用规则和库存类身份 |
| 设置 `active`、`canPurchase=true`  | 可以继续校验采购规则           | 不自动授予领用权                           |
| `canSell` 任意值                   | 不用于采购授权                 | 不用于领用授权                             |
| `managementMode=nonStock`          | 可以作为非库存采购需求         | 首期拒绝                                   |

没有设置采用拒绝规则，不自动创建默认公司设置。目录读取者仍可按既有权限查看共享物料；业务选择接口只返回本业务可用项，不能靠“前端禁用”代替提交校验。主管维护公司设置时，变更与申请提交、治理结果确认按同一引用锁顺序协调。

### 别名及单位

只读取当前主体与全局的已启用别名、旧码，不读取其他公司映射。按 A1 已有的 Unicode 规范化、去首尾空白等规则检索，保留原文。精确匹配候选需先按当前业务准入过滤，再合并去重；跨公司候选不计入数量、提示或自动匹配判断。

同一叫法的公司映射和全局映射合并后，只有全部有效命中均落在同一个具体 SKU，才可提出自动带出的候选。出现多个 SKU，或仍有仅指向统一名称的有效映射时，要求人工选规格，不用“公司映射优先”隐藏歧义。模糊搜索结果始终由人选择；确认前展示编码、规格、基准单位和业务包装。

包装必须是该 SKU 的启用规则，带出固定比例及实际版本。A1 公共详情未保证返回所有版本字段，A2 的业务详情响应补齐所需快照，不能把缺失版本当作 `0`。保存、提交、接受治理结果以及未来执行前都在事务中重查引用，不信任浏览器缓存的可用状态。

## 治理来源关联与原子回写

### 来源表和版本含义

A1 的 `materialRequests` 继续表示治理任务，`materialRequestLinks` 继续只表示任务与 SKU 的 `proposed/resolved` 关系。新增 `materialRequestSources` 表达业务来源，不能把采购或领用申请 ID 塞进现有 SKU 接口的 `requestId`。

| 字段                                                  | 含义                                                                             |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| `id`、`requestId`                                     | 关联 ID 与真实治理任务 ID                                                        |
| `sourceKind`                                          | 代码固定为 `purchaseRequestLine` 或 `materialIssueRequestLine`，不接受任意集合名 |
| `purchaseRequestLineId`、`materialIssueRequestLineId` | 两个可空外键恰有一个非空，并与 `sourceKind` 一致                                 |
| `sourceDocumentId`、`subjectId`                       | 来源父单及主体，服务端根据真实行填入并核对                                       |
| `sourceInputRevision`、`sourceEpoch`                  | 建立关联时的需求输入版本和整单治理有效期版本                                     |
| `sourceAttempt`、`revision`                           | 本行显式提报轮次和关联版本；普通失败重试沿用当前轮次                             |
| `status`                                              | `pending`、`needsInformation`、`offered`、`applied` 或 `invalidated`             |
| `proposedSkuId`、`offeredAt`                          | 治理返回的具体物料；它不等于来源行已经接受的 `skuId`                             |
| `inputSnapshot`、`resolutionSnapshot`                 | 最小需求依据及处理结果；不包含整单价格、完整人员档案或无关行                     |
| `requestedBy`、`sourceHandlerId`、原因和时间          | 发起人、当前获授权的来源办理人及追溯信息                                         |

为两个具体来源外键分别建立“来源行 + 输入版本 + 治理有效期 + 提报轮次”的唯一约束，并建立任务和主体索引。来源行通过 `activeSourceLinkId` 指向当前关联。重复提报复用同一有效关联；旧关联失效后，显式重新提报需带当前行及旧关联版本、填写原因并增加本行轮次，旧关联保留。两个并发重新提报只能有一个推进轮次，不能换一个请求键就重复创建。

首期一条来源行的每轮提报对应一个治理任务，来源表的治理 `requestId` 另建唯一约束，保证一个任务只有一条业务来源；即使多行相似，也不自动合并不同公司的任务。同一个启用 SKU 可以解决多个独立任务。A2 不提供多来源批量合并办结，避免跨公司一次办理放大事务与权限边界。

三个版本各自有明确用途：`revision` 防止旧表单及旧动作；`inputRevision` 标识本行的名称、规格、数量、单位和用途需求；`governanceEpoch` 在主动撤回、退回、取消、另行修订及主体变更时推进。仅调整另一行、返回候选或确认其他行，不使本行的来源依据自然失效。

### 创建和办结事务

跨业务联动必须在同一个 `DatabaseConnection` 中完成。现有 `MaterialService.saveInTransaction/fireInTransaction` 与选料/供应商事务入口已供采购复用，公共save/fire保留事务包装；不从采购服务嵌套独立提交。

公共数据库锁顺序为：**组织引用锁 → A2供需协调锁 → 物料主数据锁 → 具体父单、明细和关联的版本条件更新**。新增 `supplyChainMutationLock` 固定协调行，首期用于需求与治理跨表一致性；不承担未来库存维度锁。需要多个同类记录时按稳定 ID 排序，所有参与路径遵循相同顺序。

未知行提报的事务依次执行：

1. 验证登录和提报动作，取得服务器计算的公司与本人范围。
2. 取得锁后，从同一事务读取来源父单和行，校验输入版本、主体、经办资格及原始需求。
3. 查找本行本版本本有效期的关联；有相同记录就返回，不重复创建。
4. 通过共享运行时创建并提交真实治理任务，建立来源关联，更新行进度与父单版本。
5. 写两域审计和必要生命周期日志；任何一步失败整笔回滚。

治理任务办结的事务依次执行：

1. 校验治理办理权限及该任务范围，定位受控来源关联，不授予治理人整张来源申请的普通编辑权。
2. 依次取得组织、物料和 A2 锁，在事务内重查任务、来源关联、父单与目标行。
3. 校验当前关联仍有效，父单未取消，行未取消，主体一致，`inputRevision`、`governanceEpoch` 和当前关联指针均匹配；重新核查来源办理人当前仍具备该来源的确认范围。撤权时停止回写，交接给新办理人须另行授权并留原因。
4. 校验治理候选为启用 SKU；管理方式及来源公司业务准入必须满足对应模块规则。单位不明时允许返回待确认候选，不能假设换算。
5. 通过官方 `resolve` 推进治理任务，保留任务与 SKU 的办结关联；在同一事务通过来源申请的系统自迁移登记 `offered` 候选和 `awaitingConfirmation` 进度，更新版本及两域审计。
6. 全部成功后提交。返回候选失败时，治理任务也不能显示已经成功办结；不将来源回写放在提交后的 effect 中补救。

A1 的独立任务没有来源关联时保持原办结行为。所有治理办结入口，包括既有任务页面，都走同一来源检查；不能留下一个旧接口可绕过来源回写的路径。

### 接受结果和失效恢复

申请方接受候选时，使用当前父单版本、行版本和关联版本发起受控动作。在共同事务内重查授权、来源依据、SKU、公司准入、包装和数量精度，写入正式 `skuId` 及需求换算快照，将关联标为 `applied`，并写入确认人和历史。

若申请已提交或已批准，接受新的具体物料属于内容变化：保留原快照、结束原审核任务，申请回草稿并增加 `contentVersion`，新内容重新审核。待确认候选的出现不会自行改动批准内容；申请人也不能把新结果标成“与原来相同”来免审。重复接受同一结果只重放原结果，不再次退回或增加版本。

| 情况                               | 恢复方式                                                                           |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| 来源已撤回、取消、退回或输入已修订 | 拒绝旧任务办结，来源关联显示失效原因；重新提报建立当前版本关联                     |
| 单据其他行发生变化                 | 不直接判本行失效；重新读取当前父单并以版本条件提交，防止整单旧数据覆盖             |
| 治理要求补资料                     | 治理任务退回草稿，来源行显示待补充；修改原始需求后显式重新提报，不悄悄继续用旧输入 |
| 候选不符合实际需求                 | 保留候选及拒绝原因，旧关联失效；申请方修正需求或重新提报                           |
| 治理原始任务被撤回                 | 来源关联失效并提示重新提报，不让来源永远停在处理中                                 |
| 任务已办结后来源变化               | 办结历史保持原样，旧候选不能用于新版本；新需求建立新关联                           |
| 原办理人离职或撤权                 | 停止回写，授权交接后重新校验；不以服务账号或 root 绕过                             |

补充资料、退回和撤回也通过同事务来源桥接更新进度。新增来源的 SKU 独立审核必须延伸既有防自审检查：除 SKU 创建人和治理提报账号外，还要排除来源申请人、领用人绑定账号和本轮代办人，不能因为治理任务由系统代建就丢失真实提报人。

来源失效时，该行专属且尚未办结的治理任务通过新增的系统转移 `invalidateSource` 进入既有 `withdrawn` 终态，任务、关联和来源进度同事务更新，避免留下永远无法办结的待审任务。该转移只接受已核实来源操作的服务端调用；已办结任务保持原结果，不强行修改终态。A1 无来源任务不受此转移影响。

### 幂等和并发

生命周期动作沿用官方请求键；创建整单、提报来源、接受结果及配置保存还要有各自的业务重放记录。新增 `supplyChainActionRequests` 保存经办账号、动作命名空间、请求键、输入指纹、目标 ID 和结果引用，与业务同事务提交；唯一键覆盖账号、命名空间和请求键。失败回滚不保留成功标记，相同键不同输入返回明确冲突。

请求先重新鉴权，再检查相同操作的已提交重放，之后才比较旧版本。响应丢失后可用原请求键重试，不重复生成申请、治理任务、审核轮次或回写。来源行版本唯一约束与当前关联指针另防“换一个请求键重复提报”。审批任务和单据版本共同阻止两人同时批准或一人退回、另一人批准都成功。

A2 请求明确区分业务 `revision` 和官方 `lifecycleVersion`：表单编辑检查前者，生命周期执行同时使用当前官方版本；来源动作再检查行和关联版本。既有 A1 动作字段 `version` 的含义保持原契约，不能把两个域的版本数字互换。

浏览器使用现有 [随机标识工具](../client/lib/random-id.ts)，同次保存或动作失败重试保持同键；修改输入后开始新动作才换键。完整页面刷新后的不确定提交按请求键查询本人操作结果，不要求用户盲目再建一张单。幂等检查不能在撤权后把旧响应和附件地址重新泄漏给无权用户。

## 权限和数据范围

复用官方 authorization 的资源、动作及数据库策略。页面访问、业务动作、记录范围分别声明，每条接口先认证、授权，再校验输入及读取记录。新业务不能直接套用 `people.*` 范围名称，也不能把存在员工账号绑定当成自动授予角色。

| 职责           | 页面与动作                                           | 记录范围及限制                                                 |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------- |
| 本人申请人     | 两类申请的读取、创建、草稿编辑、提交、撤回、物料确认 | 明确授予的公司内本人申请；不可冒填别人或查看他人整单           |
| 代办人员       | 对应模块的 `actForOthers` 及申请动作                 | 指定公司范围，另验证申请人与领用人的有效用工；保留实际经办账号 |
| 采购经办人员   | 采购申请办理、供应商选用                             | 获授权公司；不因采购角色获得物料建码和审核权                   |
| 领用经办人员   | 领用申请办理、用途使用                               | 获授权公司；不因领用角色获得仓库出库权                         |
| 需求审核人     | 本模块 `review`                                      | 公司范围内且属于当前审核任务候选；禁止自审及审批旧提交快照     |
| 供应商主档维护 | 公共身份维护、公司使用关系维护分别授权               | 公司使用关系按主体裁剪；身份维护不能自动开放所有公司业务       |
| 领用基础维护   | 用途维护、领用规则配置                               | 指定公司范围；审核人配置另受配置维护动作控制                   |
| 物料治理人员   | 原有任务办理及新增 `materials.sources.read/resolve`  | 仅本公司或指定任务的最小来源信息；不获得整单读取或普通更新权   |
| 集团监督人员   | 两类申请及审计读取                                   | 显式列出的主体，跨公司统计按相同范围；读取不授予办理           |
| 权限管理员     | 既有官方权限管理                                     | 配置权限集和公司范围；不写业务批准结果                         |

拟新增 `procurement.requests`、`procurement.suppliers`、`requisitions.requests`、`requisitions.purposes`、`materials.sources` 等 composite，申请动作明确区分 `read/create/update/submit/withdraw/review/confirmMaterial/cancel/actForOthers`。配置读写放在独立 settings 资源；列表、详情和动作返回的可用操作由服务端结合实时资格计算。

范围至少包括本域 `ownRequests`、`ownCompany` 和显式 `companies`。本人范围需要同时核对真实申请人、创建或授权代办关系及获准公司，不允许客户端任意选择员工 ID 扩大范围。审核候选事实只是办理条件，还须有本次业务动作和公司范围；不因为任务里存过某个账号就永久放行。

人员、部门和岗位选择提供本业务专用的最小查询，返回 ID、姓名或名称、所属主体、部门及有效状态。手机号、证件、人才评价及其他人事资料不在授权字段内。无权查看的关联返回统一不可用提示，不从错误、联想或计数泄漏对象是否存在。

来源桥接只允许从已授权治理任务定位一个明确来源行，并使用代码声明的字段集合及动作约束。服务端内部取得来源数据用于完整性检查不等于允许返回数据；客户端传入任意来源类型、公司或父单不能扩大该能力。附件、历史、来源摘要及列表聚合都复用当前父单范围。

新增种子准备采购申请人、采购经办、采购审核、供应商维护、领用申请人、领用经办、领用审核、领用基础维护及供需审计等权限模板，按职责组合页面、动作和可编辑范围。既有安装采用新的增量初始化，不覆盖管理员改过的旧模板；不自动给真实账号分配角色。实际职责人和公司列表由业务确认后配置，现有后台继续管理。

## 私有需求附件

复用已注册 `@nocobase/app-plugin-file` `1.0.0-beta.23`、公开 File Repository 和现有 `nocobase-file-component-ui`。新增独立 `supplyChainFiles` 元数据及 `supplyChainFileLinks`，不把员工照片表当作通用附件表。文件链接明确属于采购或领用父单，可选指向该单某行；归属、公司和上传账号从真实父单及会话确定。

先保存有主体的草稿，再上传附件。标准文件接口的范围中间件读取真实父单并验证草稿可编辑，服务端策略写入上传者及主体默认值。上传、元数据查询和内容下载都要独立鉴权；文件内容通过同源受控 stream 路径提供，不使用公开存储 URL。具体资源动作及 `contentUrl` 以实施后的 OpenAPI 为准。

上传和业务保存是两个提交，不能宣称文件字节与申请同事务写入。业务保存只原子绑定已存在、当前账号有资格使用、同主体的文件 ID；保存失败保留已上传 ID，避免重复上传。附件增删属于需求内容变化，已提交或批准后必须先进入修订，旧快照仍引用原附件。

首期建议允许 JPG、PNG、WebP、PDF、DOCX、XLSX、PPTX，单文件最多 5 MiB、单据最多 10 个；multipart 请求上限要包含额外表单开销。服务端验证大小、扩展名与格式，不仅信任浏览器 MIME；Office 文件确认是对应 OOXML 容器。HTML、SVG、可执行文件和需要外部公开链接的旧 Office 格式暂不接入。预览使用已有本地组件，不向第三方发送私有文档。

未关联文件只允许上传者在仍有对应主体编辑资格时读取；绑定后每次按当前父单和附件用途校验，上传者不能绕过撤权。治理人员仅能读取业务方明确提供给治理的行附件，不因任务来源获得整单所有附件。文件绑定记录增加 `shareWithGovernance`，由申请方明确选择，默认关闭。

已被当前单据或历史快照引用的文件拒绝元数据删除。取消申请不删除历史文件；移除当前关联不删除旧快照引用。File Repository 的元数据删除不等于物理对象清理，本期未关联对象保留私有，后续清理必须核对全部引用并通过受控运维能力执行，不添加猜测路径的定时删除脚本。

## 拟新增接口与错误恢复

下表是 A2 整体目标契约。两类 `materialOptions` 及需求预览 `materialSelections`、供应商接口和页面、采购申请及审核配置已发布，见 [采购发布记录](采购A2.2发布记录.md)。领用用途、申请及配置在 A2.3 实施，正式治理来源、结果确认与回写及私有需求附件在 A2.4 实施。实际接口使用 `describeRoute()`、`apiValidator()`、标准 `{ data }` 和 `ApiError`，并在完成后重新获取 OpenAPI 核对。

| 接口族                                                                  | 操作与输入要点                                                                                  |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `/api/procurement/requests`                                             | GET 分页列表、POST 创建；创建携带请求键，服务端生成单号                                         |
| `/api/requisitions/requests`                                            | 同上，使用领用单头与明细 schema                                                                 |
| 两类 `/requests/{id}`                                                   | GET 完整详情、PATCH 草稿；传父单版本和稳定行 ID，包含行版本及明确取消列表，不以遗漏某行暗示删除 |
| 两类 `/requests/{id}/{transition}`                                      | submit、approve、return、withdraw、revise、cancel 等独立 POST 动作，带版本、请求键及所需原因    |
| 两类 `/requests/{id}/lines/{lineId}/requestGovernance`                  | 对已保存未知行提报或查询有效治理关联，带行输入版本                                              |
| 两类 `/requests/{id}/lines/{lineId}/confirmMaterial`                    | 接受已返回候选，带关联版本、确认的单位包装与父单及行版本                                        |
| 两类模块 `/actionRequests/{requestKey}`                                 | 查询本人不确定提交的结果；不要求已知新建单据 ID，同样检查动作命名空间、当前公司和业务读取范围   |
| `/api/procurement/materialOptions`、`/api/requisitions/materialOptions` | 按主体和业务类型搜索物料、读取业务详情；公共目录作为内部复用能力                                |
| 两类模块 `/options`                                                     | 受控主体、部门、人员及基础资料搜索；查询有分页，不暴露完整人事资料                              |
| `/api/procurement/suppliers`                                            | 供应商查询、受控身份及公司关系维护，动作范围分别校验                                            |
| `/api/requisitions/purposes`                                            | 用途列表、维护与启停；无物理删除                                                                |
| 两类模块 `/settings`                                                    | 读取与保存完整参数组，携带配置版本和请求键                                                      |
| `/api/materials/requests/{id}/sources`                                  | 仅返回已授权任务的最小来源行摘要和状态；附件另按分享标记授权                                    |
| 官方文件资源及受控内容路径                                              | 上传、元数据查询、内容下载，复用 File Repository 生成契约与作用域中间件                         |

列表、详情、关联和历史统一按公司范围读取。跨范围 ID 用一致的不可见响应，缺少动作权限在记录查询前拒绝。错误 `reason` 区分版本冲突、请求键复用、来源失效、公司未准入、单位不匹配、审核候选空缺和无效引用，前端依据原因而非英文 message 分支。

提交期间禁止重复点击和关闭，网络失败保留表单、原因及已上传附件。版本冲突展示当前值并保留本地输入，由用户明确合并再提交；不得直接换新版本重发旧整单。中文输入组合期间不触发搜索提交。数量和单位错误定位到实际行字段，首错可聚焦，窄屏将明细改成可展开行卡片。

详情刷新要覆盖申请、明细、治理进度、审核任务、历史及附件；动作返回简略信息时重新读取完整详情。沿用语义主题、键盘操作、中英文文案及 HTTP 可用请求键，不只在 localhost 验证。

## 验收场景

| 场景                       | 必须观察到的结果                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------- |
| 已知 SKU，基准单位申请     | 保存、提交、批准后规格、数量和单位不变，刷新及重启可读                                |
| 相同 SKU 两种“箱”          | 必须明确具体包装；按所选比例计算，不能只凭单位名称带出                                |
| 十进制边界与散装计量       | 超精度、溢出、不确定吨立方米换算被拒绝，原始需求保留                                  |
| 已知与未知行混合           | 可以提交并审批；仅未知行建任务，各行识别进度清晰                                      |
| 审核先完成                 | 显示已批准且仍待物料；治理不会篡改批准快照，确认新物料后重新审批                      |
| 治理先完成                 | 结果进入准确来源行；待审批内容发生确认变更后，旧审核任务不能批准                      |
| 多行依次确认               | 确认第一行不使第二行的未变需求失效；全部核对后只需重新提交一次                        |
| 更新其他行或改变排序       | 结果仍定位稳定行 ID；不写入相邻行或覆盖整单旧值                                       |
| 主动撤回、退回、取消或修订 | 迟到办结被拒绝，治理任务与来源无部分提交；旧候选不覆盖新版本                          |
| 改名、停用或撤销公司准入   | 历史快照保留；新提交、接受结果及未来执行按实时规则拒绝                                |
| 无公司设置及业务开关       | 采购缺失设置或禁采拒绝；领用不借 `canSell` 或 `canPurchase` 放行                      |
| 全局与公司别名歧义         | 只在本主体范围合并；多个候选不自动选，不泄漏其他公司命中数量                          |
| 非库存需求                 | 采购只能引用治理确认的 nonStock SKU；普通申请人不能改管理方式，领用首期拒绝           |
| 审核人空缺与自审           | 没有有效候选明确失败；创建人、真实申请人、领用人及代办人不能自审或审核关联 SKU        |
| 配置修改与重提             | 已提交记录保留原参数快照，新记录采用新配置；旧审核任务不被静默换人                    |
| 本人、他人及跨公司         | 列表、详情、选项、统计、历史、来源摘要均执行相同范围；伪造主体及人员被拒绝            |
| 匿名、页面单独授权及撤权   | API 拒绝；治理来源关联、旧请求键和上传者身份均不能绕过                                |
| 同键重试与换键重复         | 不重复建单、任务或回写；相同键不同输入冲突，换键也受来源唯一约束保护                  |
| 同时批准与退回             | 只有一个决定及一组业务、生命周期和审计事实提交                                        |
| 治理或确认中途失败         | 通过注入失败证明任务、关联、来源明细、生命周期和两域审计一起回滚                      |
| 附件上传后保存失败         | 文件 ID 和表单保留；不重复上传，未授权人不能枚举、绑定或下载                          |
| 行附件提供给治理           | 仅显示明确分享的文件；无分享权限、撤权或来源失效后读取被拒绝                          |
| 真实附件预览               | 允许格式在开发与服务后的生产构建中预览、下载，失败可恢复且无第三方私有文件外传        |
| 浏览器与 HTTP              | 中文输入、窄屏、双语、嵌套返回、冲突恢复和没有 randomUUID 的局域网 HTTP 均可用        |
| 迁移与重启                 | 隔离库 up/down 正确；真实 PostgreSQL 中并发、回滚、审核快照、附件绑定和重启持久化通过 |

### 已实现接口

| 接口                                        | 行为                                                               |
| ------------------------------------------- | ------------------------------------------------------------------ |
| `GET /api/procurement/materialOptions`      | 主体必填，按采购准入检索启用物料；支持关键词、标准名称和分页       |
| `GET /api/requisitions/materialOptions`     | 按本公司启用使用关系选择库存类物料，独立于采购和销售开关           |
| 两类 `/materialOptions/{id}?subjectId=...`  | 查询本主体、本业务可用的物料详情，包含公司/全局别名及包装 revision |
| `POST /api/procurement/materialSelections`  | 校验已知或未知需求，返回需求快照；不创建采购申请或治理任务         |
| `POST /api/requisitions/materialSelections` | 同上，已知物料限制为库存类；未知物料仍保留原始描述和单位           |

已知需求输入示例，ID 替换为授权范围内真实对象：

```json
{
  "kind": "known",
  "subjectId": "公司 UUID",
  "skuId": "物料 UUID",
  "quantity": "10",
  "unitId": "业务单位 UUID",
  "unitRuleId": "具体包装规则 UUID"
}
```

以基准单位申请时可以省略 `unitRuleId`；其他单位必须指定属于该 SKU 的启用包装规则。快照包含 `skuRevision`、包装 revision、固定比例和精确基准需求量。不存在可靠换算、超单位精度或结果溢出时拒绝，不能四舍五入或猜测单位关系。该预览不预留库存，正式提交仍须重新校验。

未知需求使用 `kind=unknown`，保存原始 `originalName`、`originalSpecification`、`requestedUnitText` 和字符串数量。响应为 `identificationStatus=unidentified`，SKU 和基准数量为空。客户端不能附加管理方式字段自行绕过治理。

查询的 `meta.aliasMatch` 区分 `none/unique/ambiguous`，只有授权主体内精确别名唯一指向可用 SKU 才带出 `skuId`。模糊命中或存在统一名称候选时不自动确定具体物料；其他公司命中不影响提示、统计或匹配结果。既有公共目录继续只使用全局别名。
