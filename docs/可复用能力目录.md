## 提取原则

1. 官方插件已有能力，优先调用；官方组件已有实现，优先组合。
2. 应用内已有功能先引用，再扩展。与组织无关的共享代码进入 client/components、client/hooks 或 server/providers 的独立服务。
3. 两个真实业务场景出现重复时再提取共性；组织约束、审批规则、数据权限不抽成绕开业务校验的万能配置。
4. 每次提取保留原调用行为，补充必要验证，更新本目录写清入口、用法、边界。
5. 跨应用发布才引入独立插件包；当前没有额外发布包。

## A2.2 供应商后端本地能力

- `SupplierService` 维护唯一 `businessPartners` 公共身份及 `partnerSubjectSettings` 的 supplier 公司关系；未来采购申请提交必须同时重查公共身份、关系和业务承担主体的启用状态，不能只验证身份存在。
- `procurement.suppliers` 的 read/create/updateRelationship/updateIdentity/linkIdentity 分别授权；公司人员不能借关系编辑公共身份。列表/详情/历史/公司选项都绑定业务策略。
- `supplyChainMutationLock`、`supplyChainAudit`、`supplyChainActionRequests` 本地建立，供应商已验证共同事务及重放；申请接入仍需新增真实模型/约束，不把供应商接口当采购申请。未来锁顺序为组织 → 供需 → 物料。
- 当前服务对共享生命周期使用官方 Repository.validateMutation 核对写字段，并检查写入前后 scope；可作为下一个真实业务集成的参考，不复刻权限系统。

本批未部署。用户后续已明确适用范围及分层停用，已补后端，页面仍待实现；不重复询问原业务问题。验证及边界见 [实施记录](采购供应商A2.2实施记录.md) 和 [当前适用规则](供应商客户适用范围与停用规则.md)。

`partner-applicability.ts` 提供 supplier/customer 角色独立的区域及公司范围判定；SupplierService 的 supplierOptions/availability 和 resolveSupplierInTransaction 已接入。全部适用不复制公司记录，单公司覆盖可以缺省；全局恢复保留局部停用。后续客户服务复用角色/范围模型及判定，不另建客户专用组织或区域字典；当前没有客户管理 API。
