# 工程经验与复用

在新增功能、排障或部署之前，按任务阅读 [开发经验与踩坑记录](../../docs/开发经验与踩坑记录.md) 和 [可复用能力目录](../../docs/可复用能力目录.md)。

- 用户明确要求：新增登录、权限、附件、导入导出、消息、审批、打印等具体功能块或基础服务前，先检查已注册官方能力，再搜索 GitHub 的现成插件、组件或库，尽量复用。优先顺序：现有官方能力 → 官方 V3 插件/组件 → 兼容且维护中的社区实现 → 应用内已有能力 → 必要自研。
- 企业业务模型（例如主体、板块、区域、部门和岗位的关系）按已确认设计实现；不要将整个业务领域作为“找一个完整插件替换”的对象，也不要为了泛化调研耽误当前交付。
- 功能块检索结论写入 [GitHub 复用调研记录](../../docs/GitHub复用调研记录.md)：日期、具体能力、候选仓库、版本兼容、许可证、维护状态及取舍。星数不能代替检查；V2 插件和演示项目不能直接视为 V3 成品。
- 基础能力自研前写明现成方案的具体差距；已核查且版本未变化的能力直接引用记录，避免重复调研。
- 实际踩坑记录现象、原因、解决办法、验证；不要记录密码、令牌、业务隐私。
- 提取共享能力时更新目录，写明可直接复用与仅可参考的边界。没有第二个真实场景时，避免预先建设泛化平台。
- 异步命令必须等前置操作完成并检查退出码；传输校验 SHA256 后才部署，同一环境串行发布。
- 截图和测试结果必须对应实际状态，未验证项如实说明。
- 官方同步 Skills 不写项目经验；项目经验写 docs 和本规则。

- 人事/人才相关修改先读经验文档的“人事与人力资源验收：失败分类与防复发”。构建完成后再启动浏览器验收，禁止同一 dist 同时构建与截图；覆盖页测试按当前层定位，保留底层 inert。新增失败先分类和记录根因，不无依据反复重跑。
- 字段权限按页面组织，页面与字段资源的归属集中在 `client/pages/settings/field-permission-pages.ts`；保存某个页面的字段策略时必须提交完整 catalog（默认 write）再过滤，避免抹掉其他页面的策略。预览环境是 `.preview/app` 的独立副本，`pnpm build` 后必须同步 `.preview/app/client` 并重启，否则浏览器仍加载旧资产。
- 本工具各执行会话的 PID 空间相互隔离，官方数据库测试工具会按主机/PID 清理过期 schema。同一个PostgreSQL验证库或同一个SQLite测试目录的应用测试/长驻fixture必须跨会话串行，先确认上一进程退出；`--maxWorkers=1` 只约束当前进程。重启探针保留的schema清理前不要另起同库测试。SQLite需并行时使用官方NOCOBASE_TEST_DB_SQLITE_DIRECTORY指定不同目录；不能共享默认目录。详见 [采购专项记录](../../docs/采购A2.2隔离PostgreSQL验证.md)。
- 字段权限的 UI 语义：不勾选 = 沿用默认（可写），只有 hidden/readonly 落库（buildFieldPolicies 过滤 write）；字段目录在 `server/providers/field-catalog.ts`，每字段带 `writable` 标志（computed/工作流 status/自动编号/审计/看板 manual 字段为 false），角色编辑里不可写字段的“可写”radio 灰禁用。新增字段资源必须给 writable 标注，并保持 client/locales 的 zh/en 同形。
